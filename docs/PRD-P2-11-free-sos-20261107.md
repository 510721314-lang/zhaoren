# PRD · P2-11「自由求助」（非订单关联紧急求助）

> 版本 V1.0（**定稿**）｜日期 2026-11-07｜状态：✅ 已裁定（Q1~Q4 于 2026-11-07 由产品负责人裁定，见 §6）

> 关联红线：core 附录A 第 9 条（紧急求助 MVP 口径）——本立项为该条的**扩展**，动笔前需同步修订该条口径（见 §7）

## 1. 背景与目标

**实证现状**（2026-11-07 代码核查）：

- 订单内 SOS 已闭环（`safety-report` 云函数，@VERIFIED 2026-10-13）：发起 → 写 `safety_report(active)` + `order_main.help_flag=true` + `platform_event(P0, type=safety_sos)` → 返回本人紧急联系人一键拨号；S3 订单联动转 S3.5 履约中断；静默求助可本人撤销、一键求助仅客服可解除。
- **缺口**：工作台「一键报警」在**无进行中订单**时（workbench.js L277-279），仅 toast「当前无进行中订单，上报时无法关联」+ 可拨 110 —— **云端零留痕**，平台安全侧完全无感知。用户在履约前/后的线下风险场景（如赴约途中、订单结束后的纠纷）得不到任何平台侧求助通道。

**产品决策**：补齐「无订单上下文的紧急求助」通道（自由求助），复用既有 SOS 链路与安全语义，不新造体系。

**可观察结果**：无进行中订单的用户发起求助后，平台安全侧（platform_event P0 + safety_report 台账）与订单内 SOS 同等可见，本人获得紧急联系人一键拨号，求助可按规则解除。

## 2. 范围

**最小完整旅程（P0）**：
入口（工作台一键报警，无进行中订单）→ 确认弹窗 → 上报留痕（含可选位置/备注）→ 紧急联系人一键拨号 / 110 → 求助解除（本人或客服）。

**P1 支持**：无（2026-11-07 裁定 Q3：静默自由求助砍掉——「怕被对方发现」语义在无订单场景不成立，留待后续按真实需求评估）。

**明确排除**（与订单内 SOS 同口径，避免范围蔓延）：
- 真实报警对接（110/120 自动上报）——附录A 第 9 条既有口径，不做；
- 自动位置持续上报、后台定位；
- 求助推送给好友/其他用户（仅平台安全侧可见）；
- 求助与投诉/爽约申诉联动（无订单可联动）。

**发布口径**：本功能**不进当前提审包 v1.6.97**；提审口径维持「仅订单内 SOS」。随提审后的后续版本发布。

## 3. 对象与归属口径（核心决策）

自由求助无订单上下文，归属口径定义如下（落地时需与云端实现核对，本文档只定产品口径）：

| 维度 | 订单内 SOS（现状） | 自由求助（本立项） |
|---|---|---|
| 记录载体 | `safety_report`，order_id=订单 _id | `safety_report`，**order_id 置空** + `sub_type='free'`（建议；与 `report_user` 已有的 order_id='' 先例一致） |
| 归属 | 订单（help_flag 挂订单） | **发起人本人**（openid）；无任何订单状态联动 |
| 订单联动 | S3→S3.5、help_flag | **无**（不存在订单，不触碰 13 态状态机） |
| 平台可见 | platform_event P0 `safety_sos` | platform_event P0 `safety_sos_free`（独立 type，便于安全侧区分统计与响应） |
| 参与方 | 需求方/耍伴 | 仅发起人 + 平台客服，**无对方角色** |
| 解除通道 | 一键：仅客服；静默：本人 | 见 FR-04（开放问题 Q1） |

## 4. 功能需求

### FR-01 入口与分流

| 项 | 口径 |
|---|---|
| 触发人 | 已登录用户（需求方或耍伴身份均可，不要求双角色） |
| 入口 | 工作台「一键报警」，与现状同一入口；**不扩「我的」页**（2026-11-07 裁定 Q4，上线后按使用数据评估） |
| 分流规则 | 有进行中订单（现状逻辑：取最近 S0~S5 订单）→ 走**现有订单内 SOS**，行为零变化；无进行中订单 → 进入自由求助确认弹窗（FR-02） |
| 未登录 | 拦截并引导登录（安全事件必须可归属到人，禁止匿名上报） |

### FR-02 自由求助上报

- **触发**：确认弹窗（标题「自由求助」，正文说明「将向平台安全中心上报本次求助，可附带位置与说明」）确认后提交。
- **处理规则**：
  1. 写入 `safety_report`：type=`sos`、sub_type=`free`、order_id/order_no 置空、status=`active`、location（可选，见 FR-05）、note（可选 ≤200 字，过内容安全检测，违规文本不入库——与订单内 SOS 同一规则）；
  2. 写 `platform_event` level=`P0`、type=`safety_sos_free`、payload 含 openid/location/note；
  3. 写审计留痕（category=security，action=`sos_free_report`）。
- **防重复**：同一用户存在**任何** active 自由求助时，再次点击幂等返回既有记录（含紧急联系人），不重复写 P0 事件。
- **结果反馈**：成功后弹出紧急联系人一键拨号面板（FR-03）；失败时提示「求助提交失败，请直接拨打 110」并保留拨号能力（**拨号永远可用，不依赖上报成功**——与现状同口径）。

### FR-03 紧急联系人一键拨号

- 复用订单内 SOS 的联系人读取规则：仅返回**发起人本人**的紧急联系人（≤2 个，姓名+关系+手机号），手机号解密仅发生在服务端返回给本人这一条路径，禁止任何他人可读。
- 联系人缺失时：面板降级为仅展示 110/120 拨号按钮，不阻塞求助主流程。
- 拨号失败：toast 提示手动拨打（与现状一致）。

### FR-04 求助解除

- 客服解除：复用 `resolve_sos` 管理员白名单通道，`active → resolved`（resolved_role=admin）+ P1 事件。
- 发起人解除：**允许**（2026-11-07 裁定 Q1——自由求助无对方参与方，订单内「不可自撤」的胁迫消警前提不成立）；通道复用 `resolve` 的「仅发起人本人」校验口径（去掉订单参与方角色校验，改为 reporter 本人校验），`active → resolved` + P1 事件 + 审计留痕。
- 解除后：safety_report 状态更新 + platform_event P1（`safety_sos_free_resolved`）+ 审计留痕；无订单字段可改。

### FR-05 位置与备注（可选字段）

- 位置：前端尝试取一次当前位置，成功则随上报携带（经中国经纬度粗校），**失败不阻塞**（允许无位置求助）；不做持续定位。
- 备注：≤200 字，可选；过内容安全检测（msgSecCheck，87014 拦截、异常降级词库，规则与订单内 SOS 完全一致）。

### FR-06 防滥用

- 单用户同时仅 1 条 active 自由求助（幂等兜底）。
- 频控：解除后 **10 分钟内不可再次发起**（2026-11-07 裁定 Q2，与 report_user 幂等窗口同量级）；active 期间重复点击幂等返回不计数。
- 恶意上报治理：依靠审计留痕 + 客服人工处置；MVP 不做自动封禁。

## 5. 共享规则（跨模块单一事实源）

1. **状态机**（safety_report，自由求助子集）：`active → resolved`（本人或客服解除）；静默变体已砍（Q3），`cancelled` 路径不存在；终态不可再变更。
2. **内容安全**：所有自由文本（备注）必须过安全检测，规则与订单内 SOS 单一定义。
3. **紧急联系人权限**：仅发起人本人可读自己的联系人；客服在平台侧看到的是事件台账，不通过该接口取联系人号码。
4. **拨号可用性**：110/120 拨号不依赖云端上报结果，任何失败路径下均保留。
5. **不触碰状态机红线**：自由求助全程不读写 `order_main`，不产生订单状态流水。
