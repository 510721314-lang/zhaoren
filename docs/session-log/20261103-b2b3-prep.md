## 二、B3 · `admin-action` 拆分设计

### 2.1 区块地图（682 行）

| 区块 | 行号 | 作用 | 可否抽离 |
|---|---|---|---|
| `ROLE_GRANTS` | L18-62 | action → 允许角色白名单 | **是**（纯数据） |
| `ensureAdminColls` | L63-73 | admin 集合幂等创建 | **否**（入口初始化副作用，须保留在鉴权运行时） |
| `resolveOpenidWithProxy` | L75-105 | 网关注解代理身份（`__admin_web_proxy` + key 校验，失败回落规范解析） | **是**（鉴权输入层） |
| `getConfig` / 配置读取 | 入口内 | 读 `admin_config.global`（走 `_shared/config_cache`） | **否**（保持现状，避免扩大改动面） |
| `logEvent` | L291-324 | 写 `platform_event` / `audit_log` | **是**（建议随鉴权一起抽，理由见 2.3） |
| `HANDLERS` | L464-506 | 已拆 action 的注册表 | **否**（分发核心） |
| `HANDLERS_PRE` | L501-524 | 免鉴权前置（`admin_login` / `admin_logout` / `config_public` / `claim_admin`） | **否**（**执行序在鉴权之前**，抽走会破坏时序） |
| 统一鉴权 + RBAC 门控 | L529-573 | openid → 白名单 → mock admin → token 会话 → 账号状态 → `ROLE_GRANTS` 放行 | **是**（本项主体） |
| `ctx` 注入与分发 | L576-658 | 向 33 个 `action_*.js` 注入 `operatorRole/operatorAccount/logEvent/getConfig` 等 | **否**（这是**契约边界**，必须留在入口） |

### 2.2 抽离方案

- **边界**：`L18-62`（纯数据）+ `L75-105`（代理身份解析）+ `L291-324`（`logEvent`）+ `L529-573`（鉴权/RBAC 主体）。
- **目标文件**：`cloudfunctions/admin-action/authz.js`（**函数内模块**）。
- **不放 `_shared/` 的理由（三条实测依据）**：
  1. 目前**只有 `admin-action` 需要 RBAC**；`admin-web` 只走 `_shared/admin-login.js`；
  2. `_shared` 会把文件复制进 11 个函数目录，须维护 `sync-*.ps1` 与 `check-shared-sync.js` 门禁（`_shared/sync-admin-login.ps1` 已是存量成本例证）；
  3. 放到 `_shared` 后任何 RBAC 微调都会触发"全仓副本同步 + SHA 校验 + 重新部署多函数"，与管理面变更频率不符。
- **对外接口（建议，最终以实现时确认为准）**：
  `authz({ db, log, openid, action, token, claimCtx, config }) → { ok, operatorRole, operatorAccount, errCode }`，错误码**逐字沿用**现行值。
- **改动量预估**：入口 `index.js` **净 −180 行左右**，新增 `authz.js` 约 200 行；**行为零变更**。

### 2.3 风险点

| # | 风险 | 位置 | 缓解 |
|---|---|---|---|
| 1 | 错误码契约漂移（`admin_forbidden` / `bad_token` / 账号非 active） | L529-573 | 抽离后**逐字保留**原 errCode 与 msg；A/B + `_shared/admin-action.entry.test.js` 双重守护 |
| 2 | 第 1 次鉴权顺序：`HANDLERS_PRE` 必须先于鉴权执行 | L501-524 vs L529 | 抽离**不动** `HANDLERS_PRE` 分支顺序；只替换"鉴权实现体" |
| 3 | `ctx` 注入字段被 33 个 action 依赖 | L576-658 | 字段名一个不改；`operatorRole`/`operatorAccount` 由 `authz` 返回值直接喂给原注入点 |
| 4 | `logEvent` 迁移后"鉴权失败也要留痕"可能丢失 | L291-324 + L549-573 | 若抽 `logEvent`，必须先确认鉴权失败分支仍调用同一实现（建议**先只抽 ROLE_GRANTS + 鉴权主体，`logEvent` 留在入口**，进一步降风险） |
| 5 | `ensureAdminColls` 若被误移进 authz，会改变集合创建时机 | L63-73 | **明确不抽**；保持入口首次鉴权前调用 |
| 6 | 部署后后台不可用窗口 | 全函数 | 部署做在提审后；单函数串行部署 + download SHA 核验 + deploy-log 记录回滚点 |

**据此调整 B3 最小版（推荐）**：只抽 `ROLE_GRANTS` + `L529-573` 鉴权主体 → `authz.js`；`logEvent` / `resolveOpenidWithProxy` **留在入口**。改动面从"4 区块"降到"2 区块"，风险显著下降，仍达成"入口瘦身 + RBAC 可测"的初衷。
