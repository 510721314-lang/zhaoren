# 十·八批次：站内抢单通知 + 代他人发布 + 3B 爽约走查

## Context（为什么要做）

延续「找人帮忙」小程序提审整改后的功能补全。用户在三项决策上拍板：

- **需求①（站内抢单通知）**：新需求发布后，向「耍伴设定范围内」的耍伴推送站内消息引导抢单。采纳 **P1 站内消息中心闭环**（复用既有 `system_notice`，零微信 config），不上一期微信订阅消息。
- **需求②（代他人发布）**：新增发布类型「代他人发布需求」。**强制手写签字授权**（复用 W9 宠物授权签字范式），不做轻量勾选版，因 `user_openid=creator_openid` 把付款/确认/评价/SOS 都绑定发布方，需用授权签字隔离代理关系。同时**修复既有缺口**：`publish` 分支漏写 `headcount/gender_pref`。
- **3B 爽约行为走查**：恢复此前挂起的「提交/举证/裁定」全链路验证。

技术红线不变：云函数 3s 硬超时 → 推送类长流程一律「每步落库 + 幂等 + 定时分片」，绝不塞进 `publish` 同步阻塞。中文消息、金额用分、幂等、`0` 为合法值。

- 文件：`cloudfunctions/order-timer/index.js`，新增一个 timer 分支 `processDemandNotify()`（每次定时触发运行一次）。

  1. 查 `grab_notify_pending:true` 的 `matching` 需求，`limit(BATCH)`；游标用 `created_at < lastCursor`。
  2. 对每个需求：查「范围内可接单耍伴」＝范围内(`haversineKm` ≤ 平台 `take_distance_max_km` 与耍伴 `max_distance_km` 的较小值，复用 `home-action` `loadVisitorPartner/LoadTakeDistanceCap/L632-L699` 过滤) 且 `status=approved` 且 `accept_switch=true` 且「需求场景 ∈ 耍伴 accept_scenes」且信用 ≥ `min_credit_take_order`。复用 `demand-publish` 的 `buildRecommendPartners(d)` 查询结构。
  3. 对每个命中耍伴：批量 `system_notice.add` 一条 `type:'demand_grab'`、`to_openid`=耍伴 openid、`order_id:''`、`action_key:'jump_demand'`、`action_payload:{demand_id}`（实现时核对 notices 页对 `jump_demand` 的 payload 字段名），`title` 用需求标题。
  4. 该需求全部推送完成后置 `grab_notify_pending:false`（幂等；中途超时断点续跑，`allSettled` 不因单条失败中断）。

## 批次 2：需求②代他人发布（后端 + 前端）

### 后端 demand-publish `publish` 分支
- 文件：`cloudfunctions/demand-publish/index.js`，在 `L384-L465` 校验段扩展。
- 新增字段与校验：
  - `publish_type: 'self' | 'proxy'`（白名单常量，默认 `self`）。
  - `proxy` 时必填：`service_target{name,relation,phone_mask}`（被代发人姓名/与我的关系/脱敏联系方式）、`proxy_signature_file_id`、`proxy_authorized:true`。
  - 签字校验复用 **W9 `verifySignatureFile()`**（`L67-L134`，PNG magic `89 50 4E 47`、≤2MB、SHA-256）；校验失败抛 `publish_proxy_sign_required`。
- 落地：
  - 需求 doc 写 `publish_type/service_target/proxy_auth_*`。
  - 写一条 `disclaimer_signature` 证据记录 `kind:'proxy_authorization'`（复用 `buildCheckboxEvidence`/`buildEvidence` 范式，含 `demand_id`、签字 SHA-256、`signed_at`）。
- **顺带修复缺口**：`publish` 写入分支（`L709-L764`）补上 `headcount`、`gender_pref`（前端已传，仅后端漏写；与 `update` 分支对齐）。

### 前端 publish 页
- `miniprogram/pages-v2/publish/publish.wxml` + `.js`：
  - 新增「发布类型」切换：`publish_type` 「自己发布 / 代他人发布」。
  - 选「代他人发布」时展示被代发人表单（姓名/关系/联系方式，脱敏）+ **强制手写签字浮层**，完整复用 W9 签字链路（`publish.js L491-L574` + `wxml L230-L256`，独立 canvas id `proxy-sign`），签字后 `proxySignatureFileId` 存云存储 `sign_evidence/proxy_auth_*.png`、`proxyAuthorized=true`。
  - payload 合并（`L1103-L1131` 处）加 `publish_type/service_target/proxy_signature_file_id/proxy_authorized`。
- `miniprogram/config/enums.js`：新增 `PUBLISH_TYPE` 常量（`L113` 附近，与 `MATCH_MODE` 并列）。不动 `MATCH_MODE`（代发是发布类型、非撮合模式）。

## 批次 3：3B 爽约行为走查（验证 + 必要时补位）

既有产物已就绪：order-action `submit/defense/detail`、admin-action `no_show_report_list/no_show_decide`、admin-web 爽约管理页、小程序提交/举证页、横幅入口。走查清单（用户操作）：

1. **提交**：小程序端对一个到期的已履约订单触发爽约提交（截图举证、文案 msgSecCheck）→ 生成 `no_show_report`。
2. **举证**：被申诉方在时限内提交 defense 证据（含超时后禁提验证）。
3. **裁定**：admin-web 爽约管理页看到报告 → 查看详情 → 裁定（判定爽约 / 驳回），确认 admin-action `no_show_decide` 落 credit 处罚与通知闭环。
4. 每个节点给用户可直接粘贴的云端测试入参（含 `mock_openid`）与断言语料；发现缺口则补小补丁并重新部署。
