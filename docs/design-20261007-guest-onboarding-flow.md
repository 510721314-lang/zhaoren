# 未注册访客「动作拦截 → 入驻引导链」设计稿（2026-10-07）

> 需求：未注册访问者点「发布需求」或「抢单」时**立即提示**；访问者确认后，**自动引导**完成 注册 → 完善资料 → 实名 → 考试 等系列环节，最后**回到原动作**继续。
> 本文为实施级细化稿（未动代码）。所有现状结论均带 file:line 证据（2026-10-07 只读调研）。

## 0. 现状与断链（只读调研结论）

### 0.1 当前不存在任何「访客拦截 + 引导 + 回跳」机制

**可复用的现状模板**：实名引导 `showRealnameGuide`（modal → `syncLoginUser` 刷新登录态 → 跳实名页，`bootstrap.js:202-218`）+ 实名码统一识别 `isRealnameGateCode`（3 个码，`bootstrap.js:177-179`）。本设计沿用它扩展为**多步引导链**。

### 0.2 三条链的云端真实门禁顺序（SSOT —— 前端引导必须与之一致）

**A. 发布需求**（`demand-publish` action=publish）：
`publish_no_openid:242` → 表单类校验（场景/时间/红线/时长/金额/地点/AA/免责，:265-325）→ **`publish_no_user`:333（未注册）** → 账号状态 → **`publish_not_realname`:358** → 信用分 → GPS → 城市/青少年 → 写库。
→ **引导链只需 2 步：注册 → 实名 → 回发布页**。（紧急联系人缺失时云端自动补占位**不阻断**，:372-381）

**B. 接单**（`order-create` action=create_from_take）：
`order_no_openid:169` → `order_no_user:307` → **`order_not_partner`:311（未入驻）** → frozen → **`order_realname_required`:321** → **`order_not_approved`:327（未过审）** → `order_switch_off:331` → 信用分 → 需求存在 → **`order_base_exam_required`:365（基础考试）** → **`order_scene_exam_required`:373/379（场景考试）** → 自单/红线/距离/时段/锁…

**C. 申请入驻（live 路径 = `partner-action` action=apply，入驻页实际调用：`partner-apply.js:84-88`）**：
`pa_no_openid:324` → `pa_no_user:342`（需已注册）→ 场景校验 →（**仅当显式传 W1 分数时才校验 ≥80**，:367-370）→ upsert `partner_profile`：新档 `status=pending_review`、`accept_switch:true`、`exam_scores` 非 W1 默认 100／W1 默认 0（:364,:401-402）——**不查实名、不查紧急联系人**（实名由接单时 order-create 兜底）。
⚠️ 另有历史云函数 `partner-apply`（独立实现，查实名/EC/W1≥80），**全仓无前端调用（孤儿）**，设计以 live 路径为准（见断链⑥）。

→ **接单引导链（v2，含前置环节）= 注册 → 实名 → 紧急联系人 → 资料维护 → 接单配置 → 考试(base·场景) → 提交入驻申请 → ★人工审核 → 回原单接单**（8 步 + 1 个异步断点）。其中**资料维护/接单配置前置到申请之前**是本设计对现状流程的调整，云端需小改（§1.8）。

### 0.3 断链清单（本设计需一并处理）

1. **无 pending intent**：登录/实名后无「回到刚才要做的动作」能力（全仓仅退出登录 reLaunch，`profile.js:379-445`）。
2. **审核异步断点**：入驻提交后是 `pending_review` 人工审核（prod `auto_approve_partner=false`），"自动引导"最多到"提交申请"；之后需通知 + 回访（审核通过 → 一键回到原单）。
3. **W1 口径矛盾**：孤儿函数硬编码 ≥80（`partner-apply:79-83`）、live apply 仅在显式传分时校验 ≥80（`partner-action:367-370`）vs 接单按 `exam_bank.pass_line` 校验（`partner-action:100`、`order-create:349-380`，FALLBACK 均 **100**）。若后台 pass_line=100，则 80–99 分会出现「入驻能提交、接单被拒」的矛盾。（✅ **2026-10-07 拍板并修复**：统一为 **100 分**（=`exam_bank.pass_line` 口径）；live 路径 `partner-action` 已改为读 pass_line（待部署，见 §3 P6）；孤儿函数随后续清理。）
4. **前端 code→步骤映射仅 3 个实名码**：未注册/未入驻/未过审/未考试等 code 全部落 toast 原文，无引导（`take-order.js:157-164`）。
5. 我的页发布入口无门禁（见 0.1 表）。
6. **双 apply 实现**：live 路径 `partner-action.apply` 与历史云函数 `partner-apply`（门禁更严：实名/EC/W1≥80）并存，后者全仓无调用（孤儿）——门禁口径不一致，建议登记、后续单独清理（不并入本批）。
7. **资料维护/接单配置只能"有档案后"操作**：资料维护要求档案存在且非 rejected（`pa_not_partner`，`partner-action:801-806`）；接单配置要求**已过审**（`pa_not_approved`，:443-447 / :471-475）。要前置到申请前，必须引入**草稿档案**（§1.8）。
8. **紧急联系人 live 路径未强制**：`apply_no_emergency` 仅在孤儿函数中；live apply 不查 EC。本设计保留 EC 为**接单链**环节（已拍板：发布链不强制、维持云端占位兜底），实施时在 live apply 或前端补齐校验。

## 1. 业务逻辑设计

### 1.1 身份状态机（判定 SSOT = 云端字段，前端只做展示态）

| 状态 | 判定（云端） | 动作放行 |
|---|---|---|
| 访客（未注册） | `peek_login` → `found=false`（`user-login:730`） | 仅浏览 |
| 已注册·未实名 | `user_account.is_realname_done=false` | 仅浏览 |
| 已实名·未入驻 | `user_account.roles` 不含 `partner` | 可发布 |
| 入驻·草稿（本次新增机制） | `partner_profile.status='draft'` | 可发布；可资料维护/接单配置/考试（**不可接单、不展示、不进审核**） |
| 入驻·待审核 | `partner_profile.status=pending_review` | 可发布 |
| 入驻·被驳回 | `status=rejected` | 可发布，可重新申请 |
| 已入驻·缺考试/配置 | `exam_scores` 未达线 / `accept_switch=false` | 可发布 |
| 可接单 | 上表全过 + 信用分/距离/时段等动态校验 | 全部 |

关键原则：**浏览永不阻断**（广场/详情/首页对访客开放），只有「发布需求」「接单」两个动作被拦截；**判定的唯一可信来源是云端字段**，前端缓存只用于快速预判，动作前以 `peek_login`/云端 code 校准（沿用现有 `syncLoginUser` 模式）。

### 1.3 引导链定义（每步完成判定 = 云端字段；完成即自动进下一步）

**发布链（短链，2+1 步）**
```
访客确认 → 注册(登录页) → 实名(实名页) → 回发布页(表单快照回填) → 正常提交
```
- 提交前把 publish 页**表单快照**存本地（storage），注册/实名回来自动回填；此后交还给云端草稿机制（`save_draft`/`list_drafts`，`publish.js:360-429`）。
- EC **不纳入发布链**（已拍板）：云端保留"缺失自动补占位"兜底（`demand-publish:372-381`）。

**接单链（长链，8 步 + 审核断点；v2：资料维护/接单配置前置）**
```
访客确认 → ①注册 → ②实名 → ③紧急联系人(contacts 页)
        → ④资料维护(bio/技能/亮点/资质证书/荣誉，partner-profile-edit 页)
        → ⑤接单配置(场景/时薪/时段/距离/日常位置，accept-config 页)
        → ⑥考试(基础 base；按所选场景考专项，如 W1，需 base 前置)
        → ⑦提交入驻申请(partner-action apply → pending_review)
        → ★人工审核 → ⑧审核通过(通知) → 回原单接单
```
- **顺序理由**：先资料/配置（决定要考哪些科目、备齐审核材料）→ 再考试 → 最后一次性送审（携带 W1 分数）；**过审即为完备状态——过审后无需再做任何配置即可接单**（现状是"过审后还要配置+考试"，这是本次前置调整的核心动机）。
- **首次提示必须预告全链**（含"审核需等待"），避免用户以为"走完就能立刻接单"。
- 引导页统一带「步骤条」（第 x/8 步）；每步完成后**自动弹下一步**（不要求用户自己找入口），中途退出可恢复（§1.5）。
- 第 ⑥ 步按所选场景收敛：未选 W1 不考 W1（`order-create:368-380` 通用规则）；选了 W1 必须在提交申请前通过（申请携带分数）。
- ④⑤⑦ 的前提是**草稿档案**已建立（§1.8）。

### 1.4 Pending Intent（回到原动作）

```js
// storage key: onboard_intent（本地即可，无需跨设备）
{
  kind: 'take' | 'publish' | 'register',
  demand_id: 'xxx',        // 仅 take 必填（32位hex）
  scene: 'W7',             // 冗余快照，失效兜底提示用
  snapshot: { ... },       // publish: 表单快照（场景/时间/时长/金额/地点/内容/备注）
  ts: 1791xxxxxxx,         // 生成时间；TTL 24h，过期自动清除
  stage: 'login'           // 断点续跑用（login/realname/ec/exam/apply/done）
}
```
- **写入时机**：访客在拦截弹窗点「去注册/去完成」时写入。
- **消费时机**：链全部完成后自动执行；take 执行前**先在线校验需求仍可接**（复用既有 `create_from_take` 失败提示兜底，如已被抢/过期）。
- `'register'`（需求②头像入口）：无 pending 动作，链完成后回「我的」页即可。
- **失效**：超过 24h、或用户明确取消（弹窗选「暂不」）→ 清除。

### 1.5 中断恢复（防丢进度）

- 首页顶部 +「我的」页新增 **「继续完成入驻」横幅**（仅当身份状态 < 接单资格 且存在 intent/或入驻进度未完成时显示，展示当前缺哪一步、点击直达该步）。
- 恢复判定顺序与 §1.3 链一致（**缺什么补什么**，已完成的步骤不重走）：注册？→实名？→EC？→base？→场景考试？→申请？→审核中（只展示）。
- 链完成 → 横幅消失 → 自动（或一键）执行 intent。

### 1.7 审核断点处理

- 提交入驻后：引导页显示「审核中」状态卡（预计审核时长文案后台可配，复用 `admin_config`）；站内通知复用现有 `system_notice` 链路（`partner-action` 已在用 `_approved`/`_rejected` 通知）。
- 审核通过：首页/我的横幅变「✅ 已通过审核，去接单」→ 若 intent 仍有效（≤24h 且需求未失效）一键回到原单接单页；失效则回广场。
- 审核驳回：横幅显示驳回原因 + 「重新申请」。

### 1.8 前置环节的云端承载：草稿档案（draft，本次新增）

现状资料维护/接单配置/考试都依附于「入驻申请」创建的 `partner_profile`；要前置到申请之前，引入**草稿档案**，走**最小改动路径**：

- **建档**：新增 `partner-action` action `init_draft`（复用 apply 的 upsert 逻辑，`partner-action:337-414`）：建/复用档案 `status='draft'`，**不授予 partner role、不进审核队列**；幂等（已存在则复用）。
- **gate 放宽（3 处小改）**：

| 位置 | 现状 | 放宽为 |
|---|---|---|
| `update_partner_profile`（资料维护） | `!me \|\| status==='rejected'` 即拒（:801-806） | 追加允许 `draft` |
| `update_config`（接单配置） | `status!=='approved'` 即拒（:471-475） | 追加允许 `draft` |
| `set_switch`（接单开关） | `status!=='approved'` 即拒（:443-447） | 追加允许 `draft`（关闭时的"进行中订单"检查对 draft 天然无碍） |
| 考试 `get_exam_questions`/`submit_exam` | 要求档案存在（:680-681） | **draft 天然满足，无需改** |

- **提交申请**：复用现有 `partner-action apply`——档案已存在时走 patch 分支（`draft → pending_review`，:380-395），**不需要新提交接口**；提交页（`partner-apply.js`）预填 ⑤ 已选的场景/位置，用户确认即送审。
- **资料维护审核区**：`*_pending` 待审区 + `profile_audit_status='pending'`（:858-863）机制原样复用；管理员审核逻辑（admin-web `partner_profile_review`）不变。
- **边界**：draft 档案不接单、不展示（广场/推荐只读 `approved`）、不进审核队列；用户中途放弃可随时回归；被 rejected 后重走链时复用现有"重走申请"逻辑（:374-376 已支持）。

### 1.9 前置资料/资质总清单（"一次性完成"原则，需求①）

原则（2026-10-07 用户确认）：**"注册"（微信一键登录建号）只是链的第 ① 步；凡是"发布需求放行前"与"接单放行前"所需的资料与资质，全部收进引导链、在目标动作前一次性备齐**；链未走完期间用户仍可自由浏览，只是不能执行目标动作（浏览永不阻断）。

| 目标动作 | 放行前必须完成的"资料/资质"（含出处） | 动态校验（动作时实时判定，不进链） |
|---|---|---|
| 发布需求 | 注册建号（`publish_no_user:333`）→ **实名**（`publish_not_realname:358`） | GPS 定位、城市开关、时段红线、金额区间、青少年限额 |
| 接单（耍伴） | 注册 → 实名（`order_realname_required:321`）→ **EC 紧急联系人**（本设计新增前置）→ **资料维护** → **接单配置** → **考试 base+场景**（`order_base_exam_required:365`、`order_scene_exam_required:373-379`）→ **入驻申请+审核**（`order_not_partner:311`、`order_not_approved:327`） | 距离、时段、时间冲突、接单锁、信用分（入链时检查） |
| 发布链边界（已拍板） | 仅 注册→实名；**EC 不强制**（保留云端占位兜底 `demand-publish:372-381`） | — |

> 与现状的本质差异：现状是"用户到了动作才被云端逐个裸拒"；本设计变成"**链内一次备齐，动作零裸拒**"。

## 2. 业务流程

### 2.1 发布路径（访客）

```
访客点「发布需求」（任一入口）
  → 拦截器判定：未注册
  → 弹窗：「发布需求需先注册」+ 链预览（注册→实名，约 x 分钟）
      ├─「暂不」→ 留在原地（可继续浏览），不写 intent
      └─「去注册」→ ①表单快照存本地 ②写 intent{kind:'publish'}
  → 登录页（正常微信一键登录，登录页新增分叉：有 intent 则不回首页，继续链）
  → 实名页 → 完成
  → 自动回跳 publish 页：快照回填 + toast「已为你恢复刚才填写的内容」
  → 用户确认提交 → 云端正常受理
```

### 2.2 接单路径（访客）

```
访客点「接单」（广场/详情）
  → 拦截器判定：未注册/缺少环节
  → 弹窗（分层）：「接单需先成为耍伴」+ 全链预览
      （注册→实名→紧急联系人→资料维护→接单配置→考试→提交申请→审核通过后可接单；预计 x 分钟 + 审核时间）
      ├─「暂不」→ 不写 intent
      └─「去完成」→ 写 intent{kind:'take', demand_id}
  → 进入链：①注册 → ②实名 → ③紧急联系人
  → 建草稿档案（init_draft，链内自动，用户无感）
  → ④资料维护 → ⑤接单配置 → ⑥考试（按所选场景）
  → ⑦提交入驻申请（预填已完成的场景/位置，确认送审）
  → 提交成功 → 断点：「审核中」状态卡 + 通知
  → [人工审核通过] → 通知 + 横幅「去接单」
  → 回原单（intent 校验需求仍可接）→ 一键接单（复用 takeOrder 全链：免责→定位→建单）
```
- 中途任何一步退出 → 下次进首页/我的看到「继续完成入驻（第 x/8 步）」→ 点击直达断点。
- 若原需求已被抢/过期：回跳时提示「原需求已被接走」+ 落到该需求详情或广场。

### 2.3 已注册但缺环节的用户（非访客）

同一套拦截器，但**跳过注册步骤**，直接从第一个缺失环节开始（示例：已实名未入驻 → 点接单直接弹「需先完成耍伴入驻」→ 进入链并从缺的环节续跑（自动建 draft）→ 完成后回原单）。弹窗文案按缺口定制（沿用 `showRealnameGuide` 的"明确告知缺什么"风格）。

### 2.4 「我的」页头像触发（需求②，新增）

```
未注册访客打开「我的」页 → 点击（或双击）自己的头像（profile.wxml:6-7，当前无行为）
  → 弹提示：「完善注册后可发布需求、接单、管理订单」+ 链预览
      ├─「暂不」→ 留原地（不打扰浏览）
      └─「去注册」→ 写 intent{kind:'register'}（无 pending 动作，链走完回「我的」页）
  → 登录（＋实名，如需）→ 回「我的」页（已是登录态，页面即时刷新）
```
- **仅对未注册访客启用**；已注册用户点击头像暂无行为（"编辑头像"功能后置，本期不做）。
- **单击或双击均可触发**（已拍板；实现上绑定单击即可，双击自然包含；不引入专门的 dbltap 逻辑）。
- 与其它入口共用同一拦截器与 intent 存储；链的展示形态一致（步骤条）。
