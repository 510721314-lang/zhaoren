## 一、流程还原（正常主流程 · 三侧视角）

### 1.1 用户侧（需求方）
1. 发布需求（`demand-publish`）：选场景（W1/W8/W4/W7/W9/W10/W11/W2/W3，`enums.js SCENES`）、时段、地点、内容、预算；可选 `proxy` 代发（需手写签字授权，`PUBLISH_TYPE`）。生成 `demand`（status=matching）。
2. 「四确认」：下单前对 时间/地点/内容/费用 逐项确认（`CONFIRM_ITEMS`），落 `order_confirmations`；此阶段 IM 仅允许系统模板消息（`im-send` 四确认前限制）。
3. 支付：`order-create` 建 `order_main`（`runTransaction` 原子建单 + `order_no` 唯一索引 `uk_order_no`），状态 S0 待支付；`payment-mock.`mock_pay` 写 `fund.paid_fen` + `settle_state=pending`，S0→S2。
4. 撮合：`broadcast` 广场抢单（CAS `demand where{_id,status:'matching'}` 置 matched）或 `direct` 定向邀约（耍伴 apply → 需求方 confirm_apply 指定 matched_openid）。
5. 履约：耍伴 `start_apply`（S2→S2_6，定位快照落库）→ 需求方 `start_confirm`（→S3）→ 耍伴 `finish_apply`（S3→S3_6）→ 需求方 `finish_confirm`（→S5）。
6. 评价：需求方 S5 内评价（`evaluation-submit`，CAS S5→S8），信用分±；48h 未评 `auto_done`。
7. 售后：S8 起售后窗口内可 `complaint`（纠纷）或 `no_show`（爽约申诉）；窗口届满 `after_sale_expire`→S10 关闭。

### 1.2 服务端（云函数/调度）
- 状态机 SSOT：`_shared/order_state.js`（16 态 + 30 条 TRANSITIONS + 正交位 `eval_state/dispute_state/dispute_type/frozen/fund` + `casTransition` CAS 乐观锁）。
- 定时器 `order-timer`：每 30 分钟一轮（2026-10-28 起应急降频）；S1 15min→S6、S0 30min→S6、S2_6 15min→S10.5、S3_6 30min→S10.5、S8→S10 售后届满、S9→默认星。
- 分账/结算：`money_rules.splitOrderAmount`（总额→平台佣金+耍伴实收，默认 10%）、`settlement` 结算单、`payment-mock` 提现 + `withdraw_record`。

### 1.3 后台运营侧（admin-web）
- 配置单一源 `admin_config.doc('global')`（`CONFIG_SCHEMA` 15 组 78 项）：费率/超时窗口/信用阈值/距离/保险/爽约处罚/实名 face_mode 等，`config_set` 写入 + `config_history` 快照 + `platform_event` 审计。
- 撮合仲裁/退款/强制完成：`action_dispute_handle`（open S10→S10.5 / refund / complete）。
- 客服读聊天记录：`action_im_kefu`（按 conv_id/order 读）。
- 耍伴审核：`partner-apply`（`auto_approve_partner` 决定自动通过或 pending_review）。

## 二、异常流程（触发条件 → 系统行为 → 用户影响）

| 异常场景 | 触发条件 | 系统行为 | 用户影响 | 严重级 |
|---|---|---|---|---|

| 无人接单 | S1/S0 超时 | `order-timer` S1 15min/S0 30min →S6 释放 demand；但实际扫描周期 30min，最坏延迟至 30min+ | 资金滞留 30min 内自动释放（较慢） | P2 |
| 接单超时 | 无接单超时专属位 | 靠 S1/S0 释放，无「接单中 N 分钟」细分兜底 | 需求长时间挂起 | P1 |
| 并发抢单 | 多耍伴同时 | broadcast 用 CAS `status='matching'`→matched 原子抢单；但 `order-create` 锁 `acquireTakeLock` 异常 fail-open、无 `user_account` 也放行 | 理论存在超卖窗口 | P1 |
| 位置伪造 | 客户端手选点 | 接单距离门禁 `min(partner.max_distance_km, 50)` 用客户端坐标，`action_take` 不校验 accuracy；履约 `start_apply` 才 accuracy>50m 拦截 | 接单可绕门禁，履约才被拦 | P1 |
| 履约开始/完毕无响应 | 耍伴发起不回应 | `start_apply_timeout`/连续2次拒绝 →S10.5 争议，资金冻结 | 资金冻结待仲裁 | P2 |
| 服务者爽约 | 到点未履约 | **仅申诉制**（`canSubmitReport` 仅 S2/S3.5 且「开始时间已过」，48h 窗口）；无自动爽约判定 | 受害方须主动举证，资金滞留，**一期零赔付** | P1 |
| 用户不确认完成 | 超时 N 天 | 自动完成/默认星（`auto_done`） | 自动完成后可申诉 | P2 |
| 退款原路失败 | 微信/银行侧失败 | `mock_refund` S2/S3→S7 + `refunded_fen` + 重试（`action_pay` 原路返回逻辑） | 提示「退款处理中」 | 已覆盖 |
| 越权访问他单 | 篡改 orderId | 订单读取/操作按 openid 鉴权 | 403 | P2 复核 |
| 争议处理 | dispute open | 冻结 `frozen` 位 + S10.5；仲裁退款(S7)/完成 | 冻结期不可误操作 | 已覆盖 |

## 三、商业规则冲突（重复计费 / 状态不闭环 / 越权 / 资损）

### 3.1 商业模型冲突 —— 平台代收 vs 服务商直连分账（P0，待确认口径）
- 商业计划书明确：V1.0 为模拟支付、正式接入后走「服务商直连分账，**资金不过平台账户**」（`BP-2026Q4-商业计划书.md:322/330/516`），并把「平台代收资金（二清/资金池）」列为 P0 合规红线（`:516`）。
- 但代码实际是**平台代收代付资金池**模型：`money_rules.js:48-66 splitOrderAmount` 抽佣 10%（`DEFAULT_FEE_RATE_FEN=1000`）→ `payment-mock/action_pay.js:83-90 mock_pay` 记 `paid_fen`+`settle_state=pending`（预付款冻结）→ `order-timer` `settle_state` ready→done → `settlement` 结算单（`base_fen/fee_fen/net_fen`）→ 耍伴经 `withdraw_record` 提现。资金链路「用户付款进平台 → 平台结算给耍伴 → 耍伴提现」。
- **结论**：二者矛盾。若正式接入微信支付时沿用当前 `mock_pay/settle/withdraw` 架构，即构成 BP 自述的「平台代收资金」二清违规。**必须由产品/法务确认最终资金路由**：要么改为微信服务商分账（资金直连、平台侧只记佣金账）、要么接受平台持牌/备案的资金池模式。当前无「直连分账」相关代码实现 → **待确认**。

### 3.2 分场景佣金未实现（P2，待确认）
- BP `:207-209`「Y1 起分场景定价，替代单一 10%」；代码仅 `platform_fee_rate_fen` 单一全局值（`CONFIG_SCHEMA` 费率组），`partner_profile.scene_rates` 是耍伴各场景时薪而非平台佣金 → 分场景佣金**未实现**。

### 3.3 爽约零赔付 + 无自动兜底（P1）
- `_shared/order_state.js no.21` 明确「一期零赔付（10% 赔付本期不做，仅扣信用分/停用；已拍板）」；`no_show_rules.js:70-81 verdictOutcome` 仅扣分（`no_show_score_deduct=20`）+ 180 天滚动窗 3 次停用 7 天。
- 爽约判定**完全依赖受害方主动申诉**（`canSubmitReport` 仅 S2/S3.5 + 48h 窗口），无「约定开始时间过了 X 分钟自动判爽约」的定时兜底 → 服务者爽约后资金长期滞留、受害者需自行取证申诉。

### 3.4 状态不闭环 / 口径不一致（P2，2 处）
- `order_state no.1/no.2` 标注 S1/S0 超时「释放 demand」，但释放时是否清 `demand.matched_openid` 与 `broadcast` 抢单成功分支口径不一致（`action_timeout.js` 未同步清该字段）→ 已被抢的 demand 释放后可能残留 matched 状态，影响大厅重复展示。待确认。
- 爽约举证逾期（`defenseDeadlineOf`）「不自动关闭」，管理员径行裁定 → 申诉单可能长期悬挂。

### 3.5 越权 / 合规风险（P1）
- `partner-apply/index.js:186` `auto_approve_partner===true` 直接 `approved` 并（`:218-221`）授予 `partner` 角色跳过人工审核；默认 false，但属可误开合规开关。
- `user-login/action_account.js:181-183` 实名：prod 默认 `face_mode='wx'`，而 `faceMode!=='mock'` 一律拒绝（`:182`），且真实人脸「TODO 未实现」（`:177`）→ **prod 环境真实用户无法完成实名**（P0，上线阻断/合规）。

## 五、代码与业务不一致（页面跳转 / 接口 / 状态机）

1. **「服务商直连分账」业务承诺 vs 代码资金池实现**：见 §3.1（P0 待确认）。BP 说资金不过平台，代码 `settlement`+`withdraw_record`+`mock_pay` 是资金池。
2. **分场景佣金（BP Y1）vs 单一 `platform_fee_rate_fen`**：见 §3.2（P2 待确认）。
3. **S9「评价超时」状态机器退役但前端仍展示**：`order_state` 将 S9 收编为 `S8 + eval_state=auto_done`（`mapStatus`），前端 `enums.ORDER_STATUS.S9` 仍在枚举表中保留展示 → 前端展示与后端合并口径并存，需确认无展示错乱。
4. **`no_show` 与 `complaint` 双入口**：爽约同时走 `no_show_report`（申诉制、零赔付）与 `complaint`（纠纷仲裁、可退款）两条链，同一事实可能双立案，状态机 `dispute_type∈{complaint/no_show/refund}` 需确认唯一性。
5. **履约旧链路 vs 新双确认链路并存**：`order_state no.5`（S2直连S3）+`no.13`（S3直连S5）为旧 B1 链路保留共存，与新 `start_apply/finish_apply` 双确认（no.23-30）并存，注释声明「待 handler 切换后收口移除」——存在旧链路绕过双确认直接完成的窗口（待确认 handler 是否已切换）。
