## 1. B2 · 需求方定位确认

### 1.1 目标
与已上线 B1（耍伴侧开始履约强制留痕）**对称**：让**需求方**在 S3 履约环节做一次位置/到场确认留痕，形成「双方互证」。涉 `order-action` 行为变更。

### 1.2 流程（锁定）
1. 耍伴点「开始履约」写入 B1 留痕 → 订单进 S3（既有逻辑，不改）。
2. 需求方在订单详情 **S3 区看到「确认我已到场（定位）」入口**。
3. 用户点该入口 → 高精度定位（复用 B1 的 getLocation + 逆地理链路）→ 写 `order_main` 的需求方确认数据。
4. **不点该入口 → 不阻塞任何既有 S3 后续流程**；仅当点入口且定位失败/拒绝时，该动作 fail-closed。
5. 幂等：同一订单需求方重复确认 → 返回首次结果，不重复写。

### 1.3 数据契约（新增字段，改动前须按 §3 报批）
- `order_main.user_confirm`（对象）：`{ latitude, longitude, accuracy, address, at, by }`
- `by` = 提交者 openid（服务端取 `getWXContext().OPENID`，禁信任前端）。
- 不新建集合。

### 1.4 后端改动点
- `cloudfunctions/order-action/` 新增处理分支（建议 action 名 `user_confirm_start`；最终命名实施时报批）。
- 状态门：仅 `status === 'S3'` 允许（CAS / 前置校验）。
- 错误码：`oa_user_location_required`（该确认动作缺定位时）。
- 补该 action 的入口契约测试入参（§4 纪律：新增 fail-closed 门须同步修既有测试）。

### 1.5 前端改动点
- `miniprogram/pages-v2/order-detail/`：S3 区块加入口 + 点击走定位流程（复用 B1 的 `utils/photo-watermark.js` 定位/逆地理部分或同等链路）。
- 展示确认后状态（已确认+时间/地址）。
- **目录复用**：getLocation 隐私接口 B1 已配置（`__usePrivacyCheck__` + 后台声明），**无新增接口**。

### 1.6 风险
- 等级 **中（偏高）**：云函数行为变更 + 定位能力链路 → 必须真机验证。
- 缓解：复用 B1 基建、不新增接口与集合、非强制不阻塞主流程。

## 2. D · 评价激励后台化

### 2.1 目标
评价完成后，系统按后台配置**自动**给用户/耍伴发放激励（**现金 + 信用分**），双方**分别**配置。涉资金与 `user_account`。

### 2.2 流程（锁定）
1. 评价提交（`evaluation-submit`）成功后，判定该订单**双方均已完成评价**。
2. 满足 → 按后台配置对用户、耍伴**分别**发放：现金（mock）+ 信用分。
3. 幂等键：`(order_id, role, kind='eval_reward')`，CAS 占坑，重复不重发。
4. 发放结果落审计 + 双方站内通知。

### 2.3 配置契约（`CONFIG_SCHEMA` 新增组「评价激励」）
| 键 | 含义 | 缺省 |
|---|---|---|
| `eval_reward_user_fen` | 需求方现金激励（分） | 0 |
| `eval_reward_user_credit` | 需求方信用分激励 | 0 |
| `eval_reward_partner_fen` | 耍伴现金激励（分） | 0 |
| `eval_reward_partner_credit` | 耍伴信用分激励 | 0 |

- 缺省全 0 = 不发放（fail-closed）。
- `action_config_public.js` 同步透出（前端展示"可得激励"）。
- 后台「运营配置」页 **schema 驱动零前端改动**。
- SSOT 纪律：改配置规范源须同步说明文案（`d` 字段）。

### 2.4 资金口径（MVP 红线）
- 现金激励**必须走 mock**（`payment-mock`，写 `pay_transaction(type=eval_reward, is_mock=true)`），**禁真实打款**。
- **与打赏区分**：现有 `tip/打赏` = 用户主动付费；D = 平台自动发放。两者是不同的资金类型，流水/文案须区分。

### 2.5 信用分口径
- 变更**必须走 `_shared/credit_rules.js` 单一源** + `credit_score_log` 留痕（同 `starCreditDelta` 法）。
- 改 `_shared` 规范源须跑 `sync-credit-rules.ps1` + `check-shared-sync` 门禁。

### 2.6 后端改动点
- `cloudfunctions/evaluation-submit/`：双方评价判定 + 发放编排。
- `cloudfunctions/payment-mock/`：新增激励入账分支（mock）。
- `cloudfunctions/admin-action/`：`CONFIG_SCHEMA` 新组 + `action_config_public.js` 透出。
- 幂等落库 + `audit_log` + `system_notice`。

### 2.7 风险
- 等级 **高**：涉**资金 + user_account + 幂等**。
- 强制措施：实施后**双专家评审** + **真机回归**；串行部署 + download 核验。

## 6. 需求 B 三期 · 开始履约「双向确认」（2026-10-14 新增需求 · 设计草案）

> 决策：需求方「同意」= **硬门 → 引入中间态**（用户 2026-10-14 拍板）。
> 状态：**设计草案，待逐项拍板后实施**（未写代码）。

### 6.1 目标
耍伴点「开始履约」后，**需求方**看到「订单基本信息」弹窗，可选择 **同意/不同意 现在开始履约**，并可点「和对方交流」进入对话；实现「开始履约需双方共识」。

### 6.2 流程（按引入中间态）
1. 耍伴点「开始履约」（B1 留痕门通过）→ 订单 **`S2 → S2_7`（新中间态：待需求方同意开始）** + 通知需求方。
2. 需求方在订单详情见**弹窗**：订单基本信息（复用后端 `buildOrderSummary`）+ 三按钮。
3. 「同意」→ **`S2_7 → S3`**（写 `service_started_at` 等，沿用原 start_service 尾部逻辑）。
4. 「不同意」→ **`S2_7 → S2`**（回退；通知耍伴）〔出口待确认，见 §6.7〕。
5. 「和对方交流」→ 进 IM 会话（自由文本）〔IM 口径待确认〕。
6. 需求方未响应超时 → 〔待确认：自动同意 / 自动放弃回 S2 / 不自动〕（若自动 → 涉 `order-timer`）。

### 6.3 状态机影响（**高危**）
- `_shared/order_state.js`：新增 `S2_7`；新增迁移 `S2→S2_7`、`S2_7→S3`、`S2_7→S2`（+超时出口）；**必须同步更新 `TRANSITIONS` 白名单**（`casTransition` 事件驱动强制拦截，白名单不同步会导致合法迁移被拒）；跑 `sync-order-state.ps1` 同步三副本。
- **收窄**原 `S2→S3` 直接迁移（防绕过同意门）。
- **`S2_7` 期间既有"仅 S2"入口的可用性须逐条评估**：改期（仅 S2）、爽约申诉（S2/S3.5）、投诉（S2 起）、加时、催办、取消。

### 6.4 IM 口径
「和对方交流」需自由文本 → `im-conv/im-send` 的 `FREE_CHAT_STATUS` 需含 `S2_7`（现含 S0 等）。⚠️ 与 [rules.md §三.5](file:///c:/zhaoren/.trae/rules.md)「四确认完成前仅模板消息」冲突——需求 A 已放开 S0 自由聊天，口径已被有意放宽，需你确认 `S2_7` 同理放开。

### 6.5 前端
`order-detail`：需求方侧在 `S2_7` 弹出「订单基本信息 + 同意/不同意/交流」窗口；复用既有弹窗/半屏组件与订单概要数据。

### 6.6 风险与门禁
- 风险 **高**（状态机 + IM + timer + 双端一致）。
- 须：A/B 等价（新迁移 → `KNOWN_EVOLUTION` + 独立断言）、状态机单测、真机双角色回归、发布时序 **先客户端后云函数**（新态需新客户端识别）。

### 6.7 决策记录（2026-10-14 已锁定）
1. **「不同意」出口 = 回退 S2**（耍伴可重新发起）。
2. **超时 = 自动回 S2**（默认 30 分钟，后台可配；需 `order-timer` 新增扫描段）。
3. **IM = 放开自由文本**：`S2_7` 纳入 `im-conv/im-send` 的 `FREE_CHAT_STATUS`（与 S0 同口径）。
4. **`S2_7` 期间既有 S2 入口 = 冻结推进类**：仅保留「同意 / 不同意 / 和对方交流」；改期/申诉/投诉/取消/催办在 `S2_7` 不可用。
5. **与 B2 = 合并到同意弹窗**：同意弹窗内**一并**完成定位/到场确认，**取消 S3 的独立 B2 按钮**（`user_confirm` 随"同意"动作一并写入）。
