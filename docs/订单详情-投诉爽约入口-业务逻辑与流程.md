# 订单详情 · 投诉 / 爽约入口 — 业务逻辑与流程（付款后 → 关单前）

> 目标：定义「报告爽约 / 发起投诉 / 撤回」在订单详情页**双方向**的展示与可用范围，覆盖 **S2（付款后）→ 关单（S6/S7/S10）** 全周期。
> 状态：**已拍板并落地**（2026-10-12）。决策：**D1=S2 起全周期放开投诉**、**D2=不互斥(受冻结位约束)**、**D3=两个独立入口**、**E1=全事件族时间线**、**E2=底部独立区块**、**E3=最近 50 条**。实现见 §7/§9。

---

## 1. 目标与范围
- 起点：用户付款成功（S2）；终点：订单关闭（S6 已取消 / S7 已退款 / S10 已归档）。
- 本期仅定义**详情页入口的可见性/门槛/流程**；裁定与赔付规则沿用现有 `no_show_rules` / `dispute` 实现。

## 2. 现状盘查（三处口径不一致，是本设计的由来）

| 维度 | 现状 | 位置 |
|---|---|---|
| **状态机白名单** | `complaint_open` from = **S2, S3, S3.5, S4, S5, S8**（to=null） | `_shared/order_state.js` 迁移表 no.16 |
| **后端实现** | `complaint` 仅允许 **S5 / S8 / S9**；`no_show_report_submit` 允许 **S2 / S3.5** + 在 `start_time+48h` 内 | `order-action/action_dispute.js` |
| **前端显隐** | 投诉按钮仅在 **S5 / S8** 分支；爽约按钮在 **S2 / S3.5** 且窗口内且未超上限 | `order-detail.wxml` / `.js` |

> **核心不一致**：状态机**已允许** S2/S3/S3.5/S4 发起投诉，但后端与前端把它收窄到 S5/S8。本设计建议**以后端+前端对齐状态机**（见 §4 D1）。

### 2.1 现有门槛（精确值）
- **爽约（`canSubmitReport`）**：`order.status ∈ {S2, S3.5}` 且 `start_time>0` 且 `now ≤ start_time + reportWindowH(默认48h)`；本人同单次数 < `maxPerOrder(默认1)`。
- **爽约撤回**：仅发起人，状态 `received`/`defense`（`decided` 不可撤）。
- **投诉**：`status ∈ {S5, S8, S9}` → CAS 置 S10.5 + `frozen=true` + `dispute_state=open` + 写 `complaint` 记录。
- **投诉撤回**：仅发起人，且订单仍为 S10.5（平台未受理）；回退 `complaint_from_status` + 解冻。

## 3. 入口矩阵（建议方案）

| 订单状态 | 含义 | 报告爽约 | 发起投诉 | 撤回 |
|---|---|:---:|:---:|:---:|
| **S2** | 已付款待履约 | ✅ 且 `start_time+48h` 内、本人≤1 次 | ✅（**新开**） | — |
| **S3** | 履约中 | ❌（已开始履约，爽约不成立） | ✅（**新开**） | — |
| **S3.5** | 履约中断 | ✅ 窗口内 | ✅（**新开**） | — |
| **S4** | 部分完成待确认 | ❌ | ✅（**新开**） | — |
| **S5** | 已完成待评价 | ❌ | ✅（现状） | — |
| **S8 / S9** | 已评价 | ❌ | ✅（现状，售后窗口内） | — |
| **S10.5** | 争议处理中 | ❌ | ❌（已存在投诉） | ✅ 仅发起人、平台未受理 |
| **S6 / S7 / S10** | 已取消 / 已退款 / 已归档（**关单**） | ❌ | ❌ | ❌（仅只读回看历史） |

**原则**：
1. 付款后（S2）即有求助入口，直至关单前；关单后**只读回看**。
2. 爽约 = 「未到/未履约」语义，仅 S2/S3.5；投诉 = 「服务/履约争议」，S2 起全周期可发起。
3. 双方入口一致（**无角色差异**），冻结位（`frozen`）优先——一旦 S10.5，双方均不可再发起。

---

## 4. 关键决策点（需拍板）

- **D1｜投诉是否放开到付款后（S2/S3/S3.5/S4）？**
  建议 **是**——与状态机 no.16 对齐；否则「履约中途纠纷」无入口。代价：后端 `complaint` 白名单放宽 + **重部署 order-action**。
- **D2｜重叠区（S2/S3.5）爽约与投诉是否互斥？**
  建议 **不互斥**，但受冻结位约束：谁先发起谁冻结，后者被 `isFrozen` 拦截（现有行为）。避免误触即可。
- **D3｜入口组织**：合并为「需要帮助」，还是保留「报告爽约 / 发起投诉」两个独立按钮？
  建议 **两个独立**（语义不同，误触成本高）。

## 5. 业务流程

### 5.1 报告爽约（现状，不改）
```
发起(S2/S3.5 且在窗口内)
  → 写 no_show_report(received) + 订单 frozen=true + 通知被诉方
  → 被诉方举证(defense, 可逾期)
  → 平台裁定: upheld(成立→受害方退款通道+处罚) / rejected
  → 发起人可在受理前撤回(→ 回退 + 解冻)
```

### 5.2 发起投诉（按 D1 决定 from 范围）
```
发起(状态∈白名单)
  → CAS 置 S10.5 + frozen=true + dispute_state=open + 写 complaint 记录 + 通知对方
  → 平台处置: refund(全退→S7 / 部分退→回主轴) | complete(有评价→S8 / 无→S5)
  → 发起人可在受理前撤回 → 回退 complaint_from_status + 解冻
```

### 5.3 撤回（两条链共用）
```
仅发起人 && 平台未受理(=仍 S10.5/S10.5-受理前)
  → CAS 回退 from_status + dispute_state=resolved + frozen=false + 写流水
```

## 6. 展示层规范（订单详情页）
1. **入口按钮**：按 §3 矩阵 `wx:if` 显隐；**双方一致**。
2. **历史留痕**（本次一并补强的方向）：
   - 爽约：`noShowReports` 列表（状态/截止/裁定结果）；
   - 投诉：订单终止态显示「争议处理中 / 已裁定」；
   - **改期**：见本次已实现的「改期结果」行（S2 区块，双方可见）。
3. **状态带提示**：S10.5「争议处理中·等待平台」；关单「已取消/已退款/已归档」。
4. **关单后**：入口全隐，保留只读回看。

## 9. 订单事件时间线（新需求：所有订单相关事件在详情展示）

> 需求：**投诉、爽约上报、改期（申请/确认/拒绝）、加时、里程碑、取消、支付/退款、催办**等**所有订单相关事件**，在订单详情**双方向**可回看详情。

### 9.1 事件分类与数据源（现成，无需新建集合）

| 事件族 | 数据源 | 关键字段 |
|---|---|---|
| 状态流转（全量轴） | `order_status_log` | `from_status/to_status/action/operator/created_at` |
| 投诉 | `complaint` | `initiator_role/reason/status` |
| 爽约上报/举证/裁定 | `no_show_report` | `reporter_role/reason/status/verdict/defense_*` |
| 改期 | `order_main`（`modify_*`）+ `order_status_log` | `modify_confirmed_at/rejected_at`、`pending_modify` |
| 加时 | `order_main.pending_extend` + `order_status_log` | `add_hours/add_amount_fen/extend_*` |
| 里程碑 | `order_main.milestone.evidence` | 进度/时间/提交人 |
| 支付/退款 | `pay_transaction` | `type/amount_fen/status/created_at` |
| 催办 | `order_main.urge_logs` | 时间/角色 |

### 9.2 实现方案（已落地）

- **新增只读 action**：`order-action.timeline`（**懒加载** —— 详情首屏渲染后再异步拉取，规避 `detail` 冷启动超时，见既有「square/scene_groups 内联致冷启动超时」教训）。
- 服务端合并上述数据源 → 统一事件数组 `[{ at, type, label, actor_role, detail }]`，**按时间倒序**，`label` **角色可读化**（不复用 admin 口径）。
- 前端 `order-detail` 新增「**订单动态**」时间线区块（首屏后加载，失败不阻断主流程）。
- **双方可见**；`openid`、内部 note、风控字段**一律不外显**。

### 9.3 边界

- `order_status_log` 可能很长 → **限流**（如最近 50 条 / 或分页）。
- 关单后**仍可回看**（只读），与 §3 一致。
- 复用 admin 侧 `dispute_detail` 的四源合并思路，但**独立实现**（权限/文案口径不同）。

### 9.4 影响面

| 层 | 改动 | 部署 |
|---|---|---|
| `order-action` | 新增 `timeline` action（多源合并 + 限流 50 + 角色可读化；源=`order_status_log`/`complaint`/`no_show_report`/`pay_transaction`/`order_main.milestone.evidence`+`urge_logs`；跳过投诉类 status_log 去重） | **已重新部署 order-action** |
| `order-detail` | 新增「订单动态」时间线区块 + 懒加载（首屏后异步、失败不阻断） | 前端本地生效 |
| 测试 | `timeline` 契约用例（缺参/越权/多源合并/倒序/去重/限流/隐私）+ 更新 `ORDER_E2E_MATRIX.md` #23 | — |

### 9.5 拍板结果（2026-10-12）
- **E1** = **全部事件族**（状态流转 + 投诉 + 爽约 + 改期 + 加时 + 里程碑 + 支付/退款 + 催办）；
- **E2** = **详情页底部独立区块**（「订单动态」卡）；
- **E3** = **最近 50 条**（够用；后续如需可加分页）。
