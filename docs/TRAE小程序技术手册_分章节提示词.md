# TRAE 小程序技术开发及维护手册 —— 分章节提示词方案

> 使用方式：在 TRAE 中打开小程序项目，按顺序把下方各章节提示词粘贴到对话框发送（或先选中对应文件/目录再发送）。建议先执行第 1～5 部分并分别保存输出，最后用第 8 部分汇总成一本完整手册。

---

## 1. 项目概述、技术选型、目录结构

**建议模型：Kimi-K2.7-Code / 长上下文模型**

```text
请你作为资深小程序架构师，全面阅读当前工程源码（忽略 node_modules、dist、unpackage 等依赖和构建产物目录）。基于真实代码，输出一份 Markdown 格式的《项目总体说明》文档，必须包含以下章节：

## 1. 项目概述
- 项目定位：一句话说明小程序是做什么的
- 核心用户角色
- 核心功能清单（从页面和接口反推）

## 2. 技术栈
- 开发框架：原生微信小程序 / uni-app / Taro 等
- 语言：JS / TS
- UI 组件库
- 状态管理方案
- 网络请求库及封装方式
- 构建工具及关键 npm 依赖
- 运行环境要求（基础库版本、最低系统版本等）

## 3. 目录结构
- 用代码树展示项目根目录下的主要目录和文件
- 对每个关键目录/文件说明职责
（例如：pages/ 存放页面，components/ 存放公共组件，utils/ 存放工具函数，api/ 存放接口定义等）

## 4. 页面清单
用表格列出所有页面：
| 页面路径 | 页面名称/职责 | 主要功能点 | 是否包含登录态/权限要求 |

## 5. 全局逻辑
- app.js / main.js 中做了什么初始化
- 是否有全局拦截器（请求拦截、路由拦截、错误处理）
- 全局状态管理和跨页面通信方案
（globalData / Vuex / Pinia / 事件总线等）

要求：
- 所有内容必须基于项目源码，不得臆测
- 无法从代码中确定的信息，请明确标注“待人工确认”
- 输出为完整 Markdown 文档，代码树使用 ``` 代码块
```

## 2. 页面 / 组件调用关系图

**建议模型：Kimi-K2.7-Code / 长上下文模型**

```text
请基于项目源码，重点分析页面路由和组件引用关系，输出《页面与组件调用关系文档》。

分析范围：
- 路由配置（app.json 的 pages 列表、uni-app 的 pages.json、Taro 的路由配置）
- 各页面中的跳转调用：wx.navigateTo / wx.redirectTo / wx.switchTab / wx.reLaunch / uni.navigateTo / Taro.navigateTo 等
- 组件引用：usingComponents 配置、import 导入、模板内使用的自定义组件
- 事件触发：按钮点击、下拉刷新、页面事件（onShow/onLoad/onReachBottom）等

输出要求：
1. 每个页面的“入口位置”和“可跳转到的页面”，附触发条件（按钮文案/用户行为）
2. 每个自定义组件“被哪些页面或组件引用”清单
3. 用 Mermaid 流程图画出主要页面跳转关系，节点为页面名，边线标注“点击 xxx 跳转”
4. 标记异常：孤立页面、循环跳转（A->B->A）、跳转到未注册路由的页面
5. 如使用分包，请单独说明分包结构及主包/分包之间的关系

输出为 Markdown 文档，Mermaid 代码块用 ```mermaid 包裹。
```

## 3. API 接口文档

**建议模型：DeepSeek-V4-Pro / 文本推理能力强的模型**

```text
请全面梳理当前小程序的网络请求代码，提取所有接口调用，生成《API 接口文档》。请重点搜索：
- wx.request / uni.request / Taro.request / axios / fetch
- 项目内自己封装的 request 工具（如 utils/request.js、services/http.js）
- baseURL 定义及接口地址拼接逻辑

为每个接口输出一个章节，格式如下：

### 接口路径（如：POST /api/user/login）
- **功能说明**：根据调用页面的上下文推断业务用途
- **完整地址**：baseURL + endpoint，标注是否直连/走代理
- **请求参数**：表格列出参数名、类型、必填、来源（固定值/用户输入/本地存储）及示例
- **请求头/鉴权**：是否携带 token、Content-Type 等
- **返回结构**：根据代码中对 res.data 的使用，提取关键返回字段及类型
- **调用方**：列出哪些页面/模块调用了此接口
- **错误处理**：调用方如何 catch / 展示错误提示

要求：
- 必须从真实代码中提取参数和字段，绝不编造
- 同一接口有多个调用点时合并成一条，但列出所有调用方
- 按“认证 / 商品 / 订单 / 用户 / 支付”等维度分组
- 接口路径含动态参数时用模板示意，如 /api/order/{id}

输出完整 Markdown 文档。
```

## 4. 第三方集成说明（支付/登录/推送等）

**建议模型：DeepSeek-V4-Pro**

```text
请排查项目中所有与微信平台/第三方服务相关的集成代码，输出《第三方服务集成说明》。覆盖但不限于：
- 微信登录：wx.login、uni.login、getUserProfile、手机号快速验证
- 支付：wx.requestPayment、uni.requestPayment、Taro.requestPayment，以及支付下单、回调、验签流程
- 订阅消息 / 模板消息
- 地图、定位、分享、客服
- 文件上传 / 云开发 / 对象存储
- 推送 / 统计 / 崩溃监控
- 自定义后端接口中的第三方鉴权（OAuth、JWT 等）

对每个集成点输出：
1. 集成目的和业务场景
2. 所属文件及关键函数（文件路径 + 函数名）
3. 调用链路时序，例如：点击支付 -> 请求后端下单 -> 唤起 wx.requestPayment -> 支付成功回调 -> 刷新订单状态
4. 关键参数说明（如支付订单号、签名、回调地址），不要输出真实密钥
5. 失败与异常处理逻辑：取消支付、超时、验签失败时的处理
6. 敏感配置存放位置（如 AppSecret、API Key 在哪个文件或环境变量），只描述位置，不输出具体值

最后用 Mermaid 画一张第三方服务调用关系总览图。
```

## 5. 部署、发布、回滚 SOP

**建议模型：DeepSeek-V4-Pro / GLM 系列**

```text
请结合项目现有配置（package.json、project.config.json、manifest.json、Dockerfile、CI/CD 脚本、云函数配置等）以及小程序平台常规发布流程，编写《部署、发布与回滚维护手册》。输出 Markdown 文档：

## 一、环境说明
- 当前有几个环境（开发/测试/生产）
- 不同环境如何区分（构建参数、环境变量、后台配置）
- 各环境的 baseURL / 域名 / AppID 配置位置

## 二、构建与发布
- 安装依赖命令
- 本地开发启动方式
- 生产构建命令及产物目录
- 在开发者工具/CLI 中上传代码的步骤
- 提审、发布、灰度发布注意事项

## 三、回滚方案
- 回滚路径（微信后台版本回退 / 代码仓库 revert）
- 回滚触发条件和执行步骤
- 回滚后需人工验证的检查点

## 四、发布前检查清单
- 版本号是否更新
- request 合法域名/业务域名是否配置
- AppID 是否已切换为生产环境
- 支付、登录等敏感功能是否冒烟通过
- 服务端配置是否需要同步更新

注意：代码中无法确认的内容，以“通用做法”补充并标注“待项目组确认”。
```

## 7. UI 页面截图核对

**建议模型：Kimi-K3 / GLM-5V 等带视觉能力的模型**

```text
请结合我上传的页面截图与项目中的页面模板代码，进行 UI 一致性核对。输出核对报告：
1. 截图页面与代码中的模板结构是否一致：是否缺少模块、区块顺序是否正确
2. 静态文案、按钮文字、提示语是否与代码中的 text 一致；是否存在需要国际化的硬编码中文
3. 样式关键点：间距、颜色、字号是否疑似与设计稿不符
4. 输出问题清单：文件位置、问题描述、建议修改方式
5. 提示兼容性问题：刘海屏、安全区、不同机型文字截断等

注意：只依据截图和代码事实，不要臆测；无法确定的问题标注“需设计稿确认”。

## 使用建议

- 每执行完一个部分，把 AI 输出的 Markdown 保存下来，最后一起粘贴给“综合汇总”提示词。
- 涉及 **AppSecret、API Key、支付 key** 等内容时，让 AI 只写配置位置，不要输出真实密钥。
- 最终手册建议人工重点核对**支付回调、登录态、接口鉴权**这几个 AI 容易出错的部分。
