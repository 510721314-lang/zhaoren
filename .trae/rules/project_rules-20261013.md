# 微信小程序 · AI 协作防回退规则

核心目标：杜绝"改一个 bug，坏三个已调好的功能"。

## 0. 开工前必读（不可跳过）
动手改代码前必须先读：
1. 本文件
2. docs/FUNCTION-REGISTRY.md —— 已验证功能清单与人工验收步骤
3. docs/CHANGELOG.md —— 近期变更与回归结论
未读取就改代码视为违规。文件不存在时先提醒我创建。

## 1. 第一原则：最小改动
- 除非我明确要求，禁止对已能正常运行的代码做：重构、性能优化、统一风格、格式化、重命名、调整目录、更换写法、补注释、删除"看起来没用"的代码。
- 禁止整文件重写，禁止"重新生成整个页面"。只做增量修改。
- 单次改动默认上限：3 个文件、30 行。超出先停下来问我。
- 我让你改 A，不能顺手改 B。禁止"顺便优化""顺手修一下"。
- 看不懂某段代码用途时先问，禁止猜测后删除或改写。
- 改 WXSS 时只改目标选择器，禁止重写整个样式块、禁止改全局 app.wxss 除非点名。

## 2. 已验证代码神圣不可侵犯
- 带 // @VERIFIED 标记的函数/组件/文件表示已通过真机验证：
  - 禁止修改其内部逻辑，除非本次需求中点名要求；
  - 确需修改时，先说明"为什么必须改" + 给出向后兼容方案（旧调用方、旧字段名仍可用），等我书面批准。
- 我告诉你某功能调通后，主动提醒我加标记：// @VERIFIED 日期 已真机验证：xxx

## 3. 先说后做（我批准前不得写入文件）
动手前只输出方案，必须包含：
1. 根因定位：精确到 文件路径:行号，说明为什么错。禁止"大概是""可能是"的猜测式修改。
2. 改动清单：每个文件改哪一处，各一句话。
3. 影响面评估：对照 FUNCTION-REGISTRY 逐条比对，列出可能被波及的既有功能。
4. 风险等级：高/中/低 + 判断依据。
5. 触发以下任一条件必须停下来问我：
   - 涉及 app.json / app.js / app.wxss / project.config.json / sitemap.json / ext.json
   - 涉及公共组件、utils/、request 封装、登录态 / token 逻辑、全局状态
   - 涉及接口字段、云函数、数据库集合、缓存 key
   - 涉及基础库版本、插件、分包结构、渲染引擎、npm 依赖
   - 涉及登录、授权、支付、订阅消息、上传下载、定位等能力链路

## 4. 小程序高危改动区（碰之前必须说清后果）
| 高危项 | AI 最常犯的错误 | 强制要求 |
|---|---|---|
| app.json | 新增页面忘记注册、改动 tabBar 顺序、误删已注册路径 | 新增页面必须同步注册；禁止改动已有 tabBar 项与页面路径 |
| project.config.json | 误改 appid、miniprogramRoot、npm 打包配置 | 禁止擅自改动；确需改必须说明并单独提交 |
| project.private.config.json | 覆盖个人编译条件、勾掉"不校验合法域名" | 一律禁止修改 |
| 基础库版本 | 擅自调高导致低版本用户白屏 | 禁止改动，除非我要求 |
| 渲染引擎 | 误开 Skyline，导致 WXSS 大面积失效 | 禁止改动 renderer / rendererOptions |
| setData | 整对象覆盖、单次数据量过大、后台页调用 | 只传变化字段或用路径写法；长列表禁止整体替换 |
| 组件 properties / data | 字段改名后 WXML 引用失效 | 改名前列全部引用点，经我确认后再改 |
| 样式隔离 | 组件样式不生效就改全局 | 先说明 styleIsolation 方案，禁止直接搬进 app.wxss |
| 云函数 | 改了本地代码不部署就说"已修复" | 必须提示我"需右键上传并部署" |
| npm 包 | 装完没构建就说能用 | 必须提示我"需执行构建 npm" |

## 5. 小程序专项红线
- 页面栈：navigateTo 最多 10 层；switchTab 不能带参数；redirectTo 会销毁当前页。改动跳转逻辑必须列出受影响的返回路径。
- 生命周期：onLoad 只执行一次、onShow 每次进入都执行、tabBar 页不会触发 onUnload。改数据初始化位置时，必须说明为什么放在对应生命周期。
- 登录时序：wx.login → 自定义登录态 → 业务请求 的顺序不得打乱；禁止在 app.js 内加"顺手"的并发改造。
- 隐私协议：涉及 getUserProfile / getPhoneNumber / 相册 / 定位等，必须确认已在 app.json 的 __usePrivacyCheck__ 与小程序后台配置，否则接口静默失败。
- 合法域名：新增接口域名必须提醒我去后台配置 request 合法域名，否则真机必失败。
- 体积限制：主包 2MB、单分包 2MB、总包 20MB。新增依赖必须评估体积影响。
- 能力链路：登录、支付、授权、订阅消息、上传下载、蓝牙、定位——任何相关改动一律列为回归清单第 1 条，并标注"必须真机验证"。
- UI 改动：滚动、键盘弹起、安全区、字体、图片、rpx 适配——一律标注"需 iOS 与 Android 真机各验一遍"。

## 6. 改完必交回归验证清单（缺此项 = 任务未完成）
任何改动后必须输出：
1. 变更清单：文件 + 改了什么 + 为什么改。
2. 回归验证清单（表格）：序号｜需回归的既有功能｜验证步骤（开发者工具/真机）｜预期结果｜谁验。
3. 区分两类验证：你可在开发者工具自证的（语法、编译、Console 无报错、Network 请求字段）你自己过一遍并说明结果；必须由我人工/真机验证的明确列出，不要含糊带过。
4. 涉及云函数、npm 构建、后台配置时，在清单里单列"需我手动操作"项。
5. 禁止以"已完成""应该没问题""现在可以了"收尾而不给验证步骤。

## 7. Bug 修复纪律
- 一次只验证一个假设，禁止把多套方案同时塞进去的"扫射式修改"。
- 连续两次尝试未解决，立即停下：说明现状 + 已排除的可能 + 需要我提供什么（报错原文、开发者工具 Console 日志、复现步骤、真机表现截图）。禁止继续盲改。
- 治本不治标，禁止以下"假修复"：用 try/catch 吞掉异常；用 setTimeout / 加大延时掩盖时序问题；注释掉代码、加 return 跳过逻辑；把 wx:if 改成 hidden 绕过渲染报错；反复 setData 空对象"试试看"。
- 需要报错信息或真机表现时先向我要，禁止凭想象编造。
- **退出登录/注销类清理必须双通道**：`wx.removeStorageSync('userInfo')` 后必须补 `getApp().clearLoginUser()` 同步 globalData（profile.js 两处已示范，L469 + L504），否则 `bootstrap.isLoggedIn()` 短暂仍返回 true。不要只清 storage 忘了 globalData。
- **navigateTo/redirectTo 必须含 fail 兜底**：所有调用（含动态 url 指向运营位配置）必须补 `fail: () => wx.showToast({...})`，防止旧版遗留路径静默无反应。app.json 注册页几乎不会失败，但动态配置可能配已下线路由。
- **唯一索引验证**：`init-db` 里声明的 `{unique:true}` 只是设计意图，不等于线上已建。必须用 tcb CLI `listIndexes` 引擎回执实证，不能靠代码扫描推断。

## 10. 大型机械重构与 A/B 门禁纪律（2026-10-14 实证新增）
- A/B「0 差异」≠ 行为正确。A/B 只比较**单次调用返回值**，以下三类盲区必须各补一道独立测试：
  1. **跨调用有状态行为**（进程内缓存/锁/计数器/单例）：同一模块实例连调两次，断言第二次的副作用计数（如 DB 查询次数）下降或为 0——单调用断言永远发现不了"缓存因 TTL=NaN 永不命中"这类问题。
  2. **静默退化**（ctx 漏注入的常量/参数变 undefined，不抛错只改变行为）：静态核对「index.js 的 ctx 提供键 ⊇ handler 解构且体内真实使用的键」；机械扫描必须排除四类误报——require 路径字符串（如 `'./openid'`）、对象键名（`{openid: x}`）、解构行自身、函数体内同名局部声明。
  3. **成功路径从未走通**（A/B 两侧同抛错也判"等价"，会互相背书）：每个核心写动作至少一条用例真正穿透到落库，断言返回值 + writes 副作用（多表写入/状态 CAS/审计/通知），不能只覆盖错误码分支。
- `KNOWN_EVOLUTION` 白名单是「跳过该例比较」而非「提供保护」：每登记一例，必须另配一条独立行为断言，否则该路径永久失去回归守护。
- `_orig_baseline.js` 冻结入库常驻（A/B 锚点，**测完不删**）；修复基线时代既有 bug 时**不刷新基线**（差异走 KNOWN_EVOLUTION 留证），修复提交必须与重构提交分离。
- 多文件/多提交机械重构收尾，默认追加一次「执行者之外」的独立审查（双视角独立取证、2/2 确认才立项修复，1/1 低置信只登记）；审查只报线上故障级（注入完整性、缓存/锁单例归属、块作用域越界、鉴权顺序、事务副作用一致性），禁止凑风格问题。
- 重构中发现的既有 bug 只登记不手修；修复须单独授权、独立提交、独立回归（接单/支付等能力链路必须真机验证）。

- 接收侧配对义务（2026-10-14 实证新增，与「生成侧可穷举」配对）：新会话收取衔接提示词后，首次回执必须先做「逐条接收清点」——把提示词中每个可执行项（含 §7 待办的 ①②③ 嵌套子项）独立编号，逐条列「原文要点｜我的理解/落点｜状态（接收/存疑/不符/缺失）」；清点编号集合须与提示词显式编号项集合差集为空，缺项即停手补齐再等派活（此阶段零代码改动，与 §3 先说后做同向，不构成开工）。禁止抽样式回执、禁止折叠子项。

## 12. 上线核验与历史保全纪律（2026-10-15 实证新增）
- **顺序铁律**：云函数部署前置门禁要求「该函数已 commit」（否则 exit 6）⇒ **先 commit 再 deploy**；改动云函数必须重新部署、改动前端必须重新 preview/upload，且**部署/重传后必须 download 比对 SHA256 或看日志回执**，禁止用「脚本报了成功」代替核验。
- **禁止用包体字节数变化判断前端改动是否生效**：`minified` / `minifyWXML` 会剥离注释与缩进，注释类改动、同一元素换位置**不改变产物字节**（2026-10-15「履约凭证卡上移」即为此例）；核验手段应为 `cli close` 强制新 IDE 会话重编译 + 源码回读 + 编译 EXIT 码，而非体积数字。
- **提交信息直传中文原文**（禁止用 `\uXXXX` 转义拼串），提交后必须读 `git log -1` 回执校验；若已产生乱码且**尚未推送**，经我批准可**一次性重写该提交说明**（`reset --soft` 重放或 amend HEAD），并同步修正文档中引用的 hash；**已推送后禁止重写历史**。
- **状态机 SSOT 与 handler 层白名单必须同步**：改任一侧就要同步规则表 `no.x` 的 `from`、3 份副本（跑 `cloudfunctions/_shared/sync-*.ps1`）与对应测试断言（含反向断言），否则口径漂移（2026-10-15 规则 no.16 收窄 S5/S8 即为此例）。
- **执行环境兜底**：ToolHost 不可用时改用 Exec(code mode)，并**显式补 PATH + 全路径**调用（`C:\Program Files\nodejs\npm.cmd`、`C:\Program Files\Git\cmd\git.exe`）——该通道 PATH 精简，`git`/`node` 都不在 PATH 内。
- **推送/联网失败先验代理**：若 `github.com:443` 不通而常规域名（baidu / api.weixin.qq.com）通 = **定向阻断**（非断网、非 DNS、非仓库问题）；本机代理在 `127.0.0.1:7890` 监听、但系统代理 `ProxyEnable=0` 时，**不得改 git config / 系统设置**，仅在该次命令注入 `$env:HTTPS_PROXY=http://127.0.0.1:7890` 后重试，并用 `git ls-remote origin -h refs/heads/master` **核实远端 hash == 本地 HEAD**（禁止只看 push 回显）。PowerShell 5 下 git push 的进度走 stderr，会被标红/包成 `NativeCommandError`——**以 exit code=0 + ls-remote hash 一致为准**，勿把标红噪音误判为推送失败（2026-10-15 实证）。

## 13. 小程序前端写操作防连点与提示时序纪律（2026-10-15 实证新增）
- **真机实证（订单详情连点跳出原逻辑）**：凡「`wx.showModal` 确认 → 云调用写操作」的 handler，**禁止裸调 `wx.showModal`**。弹窗渲染存在空窗，快速连点会堆叠两个 modal：首请求 CAS 改状态 + fetchData 换掉按钮后，第二个 modal 的确认对新状态二次请求，服务端以 `oa_*_status`/`oa_status_conflict` 拒绝，前端再把含裸状态码的 `r.msg` 直接弹给用户。注意 `wx.showLoading({mask:true})` 只遮住 loading 期间；modal 弹起到点确认、以及确认后到 loading 出现前均无遮罩。
- **统一走页级互斥包装**（参照 `pages-v2/order-detail/order-detail.js` 的 `_modal`，commit 6654403）：互斥标志挂页面实例（**不入 data、不 setData**），在**弹窗前入口**即拦；放锁必须覆盖三条路径——点取消、弹窗 fail、业务 Promise 链结算（`.then(release, release)` 兜底，success 回调必须 `return` 其 Promise 链）；成功后的 fetchData 要 return 进同一条链，保证放锁时按钮已按新状态重渲染，杜绝「放锁瞬间旧按钮仍在」。
- **「取消键也是业务动作」的弹窗必须显式放行**：同意/拒绝共用一个 modal（如加时确认弹窗取消键=「拒绝加时」）时用 `cancelIsAction` 类开关让回调照常执行，禁止一律把 `!res.confirm` 当放弃处理。
- **状态冲突错误码不直出 `r.msg`**：码名匹配 `/_status$|status_conflict/` 时静默 fetchData + 固定友好文案（如「订单状态已更新, 请刷新后重试」）；权限/冷却/次数/资金/文本安全等业务错误**仍走原文案**，禁止一刀切吞掉所有 `!r.ok`。
- **成功反馈时序**：写操作成功后 loading 保持到 fetchData 刷新完成再弹成功 toast（堵慢网刷新空窗的重复点）；fetchData 类刷新函数须返回 Promise（既有调用方不接返回值，天然向后兼容）。
- **`wx.navigateTo` 的 success 回调里禁止 toast**（跨页提示在目标页多余）；返回原页所需的刷新交给 onShow 兜底，不靠跳转前 toast 交代状态。
- **修复切口**：只做「加包装器 + 逐 handler 替换调用」，不重写既有回调体；带 `// @VERIFIED` 且本次未点名的 handler 不动，未覆盖的同构 handler 在 FUNCTION-REGISTRY 单列残留项由我决定是否扩面，禁止借修 bug 顺手扩面。
- **前端锁不替代服务端幂等**：互斥锁只改善交互体验，资金/状态推进仍以服务端 CAS + 写操作不重试为准（本项目已具备）；禁止以「前端已加锁」为由放松任何服务端状态/权限校验。

## 16. 云函数批量部署 · 提交信息乱码判定 · 测试基建口径（2026-10-17 实证新增）

## 17. 前端块/组件迁移纪律 · WXSS 注释陷阱 · 门禁与网络通道判读（2026-10-17 实证新增，里程碑4 全阶段）

- **迁移类改动的前端自证 6 项（每搬一个块/组件必做，缺一即停）**：
  1. **被删标识符全仓 grep 零残留**：所有被删方法名/data 字段/`selectComponent('#id')` 必须在整个 `miniprogram/` 下**无任何代码引用**——注释里的对照说明不算（实证 4b：被删 16 个标识符只剩新组件注释提及）。
  2. **usingComponents 双向核验**：页面与组件的两份 json 里每个 `usingComponents` 目标 `<path>.js` 必须存在；并反查「页面 wxml 里出现但未注册的非原生标签」（实证 4b 全绿）。
  3. **句柄齐备**：页面/组件 wxml 里每个 `bind*`/`catch*` 的值（含 `bind:close`/`bind:sign-confirm` 这类带冒号的）都要在对应 js 找到同名方法定义（判定正则用 `(^|[^\w])method\s*\(`，防子串误判）。
  4. **标签配对**：改动过的 wxml 做 `<view>`/`<text>`/`<block>` 开闭计数比对，且**与改动前基线对比**（实证 4a 曾记「text 计数差 −1」为既有差异，勿当自己引入；4b 独立计数 view 90/90、text 34/34）。
  5. **CSS 注释配对**（见下条，4b 踩坑项）。
  6. **行数回填**：以「非空行」口径逐文件实测（`HEAD` 版 vs 工作区）并回填 plan §4/§8.4。
- **WXSS 注释里禁止出现 `*` 紧跟 `/`（2026-10-17 硬实证）**：在 WXSS 注释中写 glob 式选择器，如 `.pub__pet-doc*/.pub__pet-agree*`，其 `*/` 会被 CSS 解析器当作**注释结束符** → 注释提前闭合、残余文字成为非法 CSS → 开发者工具报 **`预览 Error: Unexpected '/'（Escaping special characters with \ may help）`**。**同形文本在 WXML 注释（`<!-- -->`）内无害**（4a 的 publish.wxml 就有同类文本且能正常编译）→ **只查 wxss**。规避写法：写 glob 时用空格/「与」/「系列」隔开。自证动作：每次改 wxss 后做注释配对复算（`/*` 计数 == `*/` 计数），并扫描文件内 `*` 紧跟 `/` 的位置（本次修前即存在此类隐性错位，修后 3/3 平衡）。
- **编译门禁通道判读：`Fetching AppID () permissions` + reset/refused ≠ 代码问题，且可逆（勿永久降级）**：`cli preview` 若停在 `- Fetching AppID () permissions` 并报 `ECONNRESET` / `connect ECONNREFUSED 127.0.0.1:7890` 且 **exit 0、无 `✔ preview`、无二维码产物** ⇒ 属 §16「成功回执误导」，根因是 **IDE/系统代理指向的 `127.0.0.1:7890` 未监听**（实证系统代理 `ProxyEnable=1` + `ProxyServer=127.0.0.1:7890`），**非代码缺陷**。处置：① 当次以「IDE 编译 + Console 无红错」放行（仅 `[Perf]`/`[system]` 信息项不算红错）；② **登记「待代理恢复后补测 cli preview」**——实证 7890 起后同一命令即得 `✔ Using AppID: <appid>` + `✔ preview` + `EXIT=0` + 体积表（4a/4b 因此均补齐硬门禁，并顺带取得主包体积用于回填 plan §1）。
- **网络「瞬时不可达」的处置：不重试、登记待复核、恢复后补一次干净核验**：`git push` 回执成功（exit 0 + `old..new branch -> branch`）后，紧随的 `ls-remote` 可能因网络**瞬时**不可达而失败（实证 `Empty reply from server` → 连续 4 次 `github.com:443 after ~21s Could not connect`，同时 7890 未监听）；随后网络可自行恢复。**处置**：**不要**在不同代理配置间反复重试（浪费），按 §15 记「已推送、`ls-remote` 待复核」为挂起项；**网络恢复后跑一次 `git -c http.proxy= -c https.proxy= ls-remote origin -h refs/heads/master`，hash == HEAD 即 §12 闭环**（实证恢复后 EXIT=0 且 hash 一致，之后 `git status -sb` 无 ahead/behind）。
- **「检查网络」标准四查（一条命令给全结论，判「定向阻断 / 断网 / 代理未监听」）**：① `Resolve-DnsName github.com`（DNS）；② `Test-NetConnection github.com -Port 443`（目标）；③ `Test-NetConnection www.baidu.com -Port 443`（对照，§12 判定向阻断）；④ `Test-NetConnection 127.0.0.1 -Port 7890` + 读 `HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的 `ProxyEnable/ProxyServer` + `git config --get http.proxy`/`https.proxy`。**要点**：git 自身**不读** Windows 系统代理（实证二者可分离——系统代理开着但 git 无代理配置），故「IDE 报代理错」与「git 能否推送」是两条独立通道，必须分别验。
- **弹层类 UI 组件化的低风险切口（4b 实证）**：组件**只承载 `position:fixed` 的弹层 + canvas**，在**页面根部按 kind 实例化两次**（如 `#pet-auth`/`#proxy-auth`）；页面流内的标题行/勾选组/文案 loader/勾选态/`wx.cloud.uploadFile` 一律留页面 → **零布局位移**，且三类差异（文案来源、实例 id、state 命名 `pet*`/`proxy*`）可原样保留。**前置判定**：先确认目标 UI 定位方式，`fixed` 者优先走此切口。多根组件（弹层与遮罩各为一个根）与 `styleIsolation:"apply-shared"`（独占样式随块迁组件 wxss、共用原语留页面）均实证可行。

## 21. CloudBase 单函数目录打包约束（2026-10-19 最危险事故实证新增）
- **铁律：云函数禁止跨目录 require。** 微信云开发按「单函数目录」打包上传，`cloudfunctions/_shared/` 不在任何函数包内。任何 `require('../...')` 在云端必 `MODULE_NOT_FOUND` → 整个云函数加载失败（`FUNCTIONS_INVOCATION_FAILED`），该函数**全部接口**不可用（后台直接读不出数据）。
- **共享代码唯一合法用法**：① canonical 置于 `cloudfunctions/_shared/`；② 建 `sync-*.ps1` 复制到各消费函数目录；③ 在 `scripts/check-shared-sync.js` 的 `SYNC_MAP` 登记；④ 函数内写 `require('./xxx')`（本地副本）。详见 `cloudfunctions/_shared/README.md`。
- **新增/修改 `_shared/*.js` 后必须先跑 `npm run verify:offline`**，确认 `check-shared-sync`（含未登记模块自动发现）与 `check-require-scope` 全绿，再部署。
- **三重假阳性警戒（本次实证：三个信号全"绿"却线上崩溃）**：
  1. 本地 `verify:offline` 全绿 ≠ 云端可加载——本地 `_shared/` 真实存在，require 能解析；云端打包后不存在；
  2. `deploy` 返回 `success=true + filesCount` ≠ 依赖完整——`filesCount` 不含 `_shared/`（实证 admin-web 48 = 44 public + 4 基础文件）；
  3. `download` 逐文件 SHA 全 MATCH ≠ 运行时可用——只证明「部署的文件两边一致」，不证明「运行时依赖齐全」。
- **部署唯一入口**：一律走 `deploy-cloud.ps1`（→ `.trae/predeploy.ps1`）。该门禁现已含 `check-shared-sync` + `check-require-scope`（2026-10-19 双专家评审 F1 补齐，与语法检查同级 fail-closed）。**禁止直接裸调 `cli.bat`**：裸调会跳过 predeploy 的全部闸门（本次事故即因裸调 cli 发生）。
- **`_shared/` 新增文件判定**：在任一函数目录存在同名副本即属「可部署共享模块」，必须登记 SYNC_MAP，否则 `check-shared-sync` 报 `[UNREGISTERED]` 拦截（fail-closed）。
- **既有漂移只登记不手修**（§10）：如 `heal.js`（canonical 含 `healAuditLock`，demand-match/order-create 为旧版）已登记 `KNOWN_DRIFT`，非阻断但每次运行显式打印并由 owed 计数；修复须单独授权 + 同步 + 重新部署。
- 与既有规则关系：§16（部署口径）/§12（上线核验）同向；§10（A/B 与白名单纪律）适用于 `KNOWN_DRIFT`。

## 23. 云函数调用身份/通道 · 造数阈值自洽 · 时段敏感测试口径（2026-10-20 G3 实施 + P3-7 修复实证新增）

- **H1 错误码前缀定位函数（先读码、再动手）**：云端调用报错时**错误码前缀即指明是哪个函数拒的**——`ot_*`（如 `ot_forbidden`）= `order-timer`；`admin_*`（如 `admin_no_openid`）= `admin-action`。把 A 函数的载荷发给 B 函数，症状就是 B 的 fail-closed 码。实证（2026-10-20）：将 `{"action":"config_set",...}` 发给 `order-timer` → 连续 3 次 `ot_forbidden` 且配置始终改不动——**根因是调错函数，重试无解**。纪律：报错先按码前缀确认「目标函数 × 事件形状」，禁止无脑重试。
- **H2 调用通道/身份矩阵**：①**改线上配置** → 运营配置页（见 H3）或 **HTTP 网关 + `X-Admin-Key`**；②**跑扫描段** → `order-timer` + `{"Type":"Timer","TriggerName":"orderTimer"}`（`Type` 大写 T、`TriggerName` 精确匹配 `orderTimer`、**不带** `mock_openid`；依据 order-timer 鉴权门）；③**云端测试面板调用不携带登录身份**，且 **prod 下 `mock_openid` 被忽略**（`resolveOpenid` fail-closed）→ 面板直调写类/鉴权类 action 必得 `*_no_openid`。**面板只能走"无身份/只读"路径，不能用于改线上配置**。

## 25. PowerShell/中文脚本编码与 BOM 纪律（2026-10-20 备份链编码事故实证新增）

- **J1 编辑工具会剥 BOM ⇒ 改完必复检并补回**：凡用文件编辑工具改动**含中文的 `.ps1`**，改完必须复检前三字节 = `EF BB BF`；缺失即补（`[System.IO.File]::ReadAllText(路径, UTF8)` → `WriteAllText(路径, 内容, New-Object System.Text.UTF8Encoding($true))`），并用 `[System.Management.Automation.Language.Parser]::ParseFile(...)` 复检 **0 错误**。实证（2026-10-20）：本次改 5 个备份链脚本，改完 **5/5 全部丢失 BOM**，当场即报「字符串未闭合 / 缺失 `)` / Unexpected token」式解析错——**即项目 20261013 记录过的 BOM 事故复现**；且 `auto-backup.ps1` 的 `Test-Bom` 会对 4 个脚本**硬 FAIL**，漏检即整链静默停摆。
- **J2 BOM-less JSON 的读写闭环（双保险）**：PS5.1 `WriteAllText(..., UTF8Encoding($false))` 写 JSON + 读端 `Get-Content -Raw`（无 BOM 时按 **GB2312** 解码）→ 中文内容可致**闭合引号被吞**、`ConvertFrom-Json` 报 `(239)` 类解析错。规范：**写端带 BOM**（`New-Object System.Text.UTF8Encoding($true)`）**且**读端显式 `-Encoding UTF8`，两端都做。本轮已覆盖：`manual-backup.ps1`（manifest + `Save-JsonWithHash`）、`backup.ps1`（同两处）、`auto-backup.ps1`（incremental 快照读写 + enc-manifest + manifest）、`raw-export-encrypted.ps1`（enc-manifest）、`restore.ps1`（manifest + admin_config + 逐集合读）。
- **J3 原生命令输出编码（git / node / cli）**：PS5.1 按 `[Console]::OutputEncoding`（中文机＝GB2312）解码**原生 stdout** → 中文必乱码；乱码落盘后再被 GB2312 读还可能**破坏 JSON 结构**。规范：取原生文本（尤其 `git log --oneline`）**前临时置 UTF8、取完还原**，**禁止全局常置**（常置会改变 `2> file` 重定向产物编码）。实证：同一进程内置 936 取 `git log` → 乱码且**尾部吞字符**；置 UTF8 → 完整中文。
- **J4 备份链代码改动后的复验口径**：`Test-Bom` 与语法解析只能证明「能加载」，**必须实跑到 `[LOG] SUCCESS`** 并核对产物（bundle / files / db_export / raw / CHECKSUMS + manifest 的 `git_short` 可读且带 BOM），再跑 `verify` 确认既有缺口消失——与 §12「部署后必须 download 核验」同构。
- **J5 PowerShell 变量名大小写不敏感 ⇒ 包装器参数名必须避开被包装代码的作用域变量名**（2026-10-20 自伤回归实证）：`function Invoke-WithRetry([scriptblock]$Body, ...)` 的参数 `$Body` 与脚本域的 `$body`（JSON 串）撞名 ⇒ 脚本块内 `-Body $body` **解析成脚本块自身** ⇒ 请求体非 JSON ⇒ 云网关 **400（响应体为空）**；症状极具误导性（像是"网关间歇故障"，且**直连调用同时成功**）。纪律：①高阶函数/包装器的参数名一律用与被包装代码无交集的词（实证改用 `$Job`）；②**网络/接口类故障先用「同点直连 vs 包装器」二分定位**（本次即靠一行 `zz-` 探针在同一运行点内做直连对照，一次定性）；③自伤回归必须复盘并登记（本次 04:30 verify 的 4 项缺口里有 1 项实为本改动引入）。
- **J6 脚本内捕获原生命令（尤 `curl.exe`）大输出 ⇒ 「落盘 + 显式 UTF8 读回」**（2026-10-20 门禁 smoke 实证）：`smoke-check.ps1` 的 `Invoke-Gw` 用 `$raw = curl.exe …` **直接**捕获 stdout，PS5.1 按 `[Console]::OutputEncoding`（中文机 GB2312/936）解码网关 UTF-8 中文 JSON → 乱码**吞闭合引号** → `ConvertFrom-Json` 抛错 → `$r = $null` → 6 项判据全 false → `SMOKE FAILED: 6 item(s)`（fail-closed，只误挡不误放）。**规范**：脚本内需捕获 native（`curl.exe` / `node` / CLI）stdout 并做 **JSON/文本解析** 时，**优先 `-o` / `>` 把字节原样落盘，再 `Get-Content -Raw -Encoding UTF8` 读回**，绕开控制台解码；较 J3「临时置 UTF8 再还原」更稳（不受 `2>` 重定向与进程级编码态影响）。**取证**：`[RAW]` dump 首部 `"ok":true` 即证故障在**解码层**而非网关。**验收**：改后 4 项 `config_public` + `system_notice` 由 FAIL 转 PASS，全链 6/6。

## 26. 业务单号/唯一标识生成与碰撞兜底纪律（2026-10-21 订单号改纯数字实证新增）

- **K1 可读化改动必须先量化熵损失**：把标识从随机 hex 改为可读形态（纯数字 / 日期前缀）时，必须书面给出「随机段位数 → 空间大小 → 等效熵 → 日单量-碰撞概率表」四件套，禁止用「随机足够」搪塞。实证（2026-10-21）：`ORD+yyyymmdd+16hex`（64 bit）→ `yyyymmdd+10 位数字`（33 bit），**熵降 31 bit**；按生日问题日 1 千单年碰撞率 1.8%、日 1 万单 84%。最终用户拍板扩到 **12 位（40 bit，20 位总长）**。
- **K2 唯一标识必须三层齐全，缺一层即未完成**：①生成端 **密码学随机**（`crypto.randomInt`，**禁止 `Math.random`**，避免可预测与取模偏置）；②数据库 **唯一索引**；③写入端 **dup-key 重试**（≤3 次，重试时重新生成而非复用）。实证：`order-create` 原仅①+②，无③ —— 碰撞即 `order_db_fail` + 需求回滚，用户看到「订单创建失败」且无重试。
- **K3 dup-key 重试必须限定在「本事务内唯一索引」范围内**：重试前先枚举该事务写入集合的 `unique:true` 索引（实证：`create_from_take` 事务仅 `order_main.uk_order_no` 一个），确认无歧义才可按任何 dup-key 触发重试；否则会掩盖其他数据完整性错误。事务原子性是重试的前提（失败尝试不残留半成品），**非事务写入路径不得照搬**。
- **K4 格式变更必须保持读侧双形态兼容**：历史数据不迁移、不改写；生成端改格式的同时，**反查/检索侧**（运营 CLI `resolveOrderId`、客服、后台搜索）必须同步扩为「新格式 or 旧格式」，并在注释写明分界日期。禁止只改生成端就宣告完成。
- **K5 「init-db 里声明了索引」≠「线上已存在」**：唯一索引的线上存在性须经控制台或受控探针实证；未证实前，台账与 CHANGELOG 只能用「已声明」措辞，**禁止写「有唯一索引兜底」这类事实性断言**（与 §24-I1「命中数 0 先怀疑过滤形态」同源的「未证实不得断言」精神）。
- **K6 概率必须与后果同表交付**：评估标识方案时，「碰撞概率」与「碰撞发生后用户/系统可见的行为」必须一并给出（本次：唯一索引缺失则静默双单、索引存在但无重试则用户报错并回滚需求）；只给概率不给后果视为评估未完成。

## 29. 凭据类输入边界 · 后台双域名口径 · 鉴权拒绝的审计反查（2026-10-25 登录 401 实证新增）

- **M1 粘贴式凭据：`trim` 只是底线，真正要防的是「整行前缀」**——三条**实测**结论（2026-10-25 网关四组探针）：
  | 输入形态 | 网关结果 | 结论 |
  |---|---|---|
  | `key` | HTTP 200 | 正常 |
  | `key + 半角空格` / `\t + key` | **HTTP 200** | 首尾**半角**空白被 HTTP 头解析剥离 → **不是 401 的原因**（此前误判） |
  | `AWK_KEY=<key>`（整行粘贴） | **HTTP 401 `bad_key`** | **真凶**；trim 无法修复 |
  | 全角空格 `U+3000` / 零宽字符 | 浏览器侧抛非法头字符异常（非 401） | 需客户端 `trim`（JS trim 覆盖 U+3000） |
  → 落地要求：① 入口统一走**归一函数**（`trim` + 剥离已知前缀），不要只 `trim`；② 归一后为空要**本地前置拒绝**并提示，不发无意义请求。
  实证落地：[admin.js](file:///c:/zhaoren/admin-web-frontend/src/api/admin.js#L33-L42) 的 `normalizeKey`（`trim` + `/^AWK_KEY\s*=\s*([\s\S]*)$/i` 剥离）；10/10 用例（plain/带前缀/大小写前缀/前后空格/全角空格/空值/null/仅前缀/整行CRLF）实测通过；云端产物字节级复核 `CLOUD_BYTES=LOCAL_BYTES=2866` 且含三标记。
- **M2 鉴权失败必须给「可操作」提示，不得透传 HTTP 客户端原文**：401/403 在网关层是「凭据不匹配」，业务语义应转成「密钥不正确：请确认不含前缀与空格 / 请重新登录」。前端拦截器的 `msg: e.message` 会把排障成本全部转嫁给用户。
- **M3 后台存在两个域名，职责不同，勿混用**：
  | 用途 | 地址 | 说明 |
  |---|---|---|
  | **静态托管（SPA 入口，测试/使用走这个）** | `https://<env>-<appid>.tcloudbaseapp.com/` | `cloudbase hosting deploy ./dist` 的落点，实测立即生效 |
  | **HTTP 网关（云函数 /api）** | `https://<env>-<id>.ap-shanghai.app.tcloudbase.com/api` | SPA 里 `BASE_URL` 硬编码指向它；其**根路径 `/` 也会返回 SPA HTML，但走 CDN 缓存**，部署后仍可能是旧构建（实测：托管域 `index-CNRxHc88.js` vs 网关域 `index-DG37DiD9.js`） |
  → 「页面没更新」先按 **M3 判域名**，再谈缓存；验证部署用 `GET /?v=<random>` + `Cache-Control: no-cache` 取 `assets/index-*.js` 哈希比对。
- **M4 鉴权拒绝有审计，排障先查库再猜**：`admin-web` 网关对密钥失败写 `platform_event`（`type=gateway_bad_key`, `payload.reason=bad_key|missing_key`, `path=/api`）。**判据**：出现该事件＝请求确实到达网关且密钥不符（不是网络/CORS）；账号登录端点免 key，因此**不会**产生该事件 → 有该事件即可排除「账号模式密码错」。取证方式：带有效 `X-Admin-Key` 调 `{"action":"event_list","limit":15}` 读最近事件。实证：7 条 `gateway_bad_key` 直接定位到「粘贴的是错值」而非「网关故障」。
- **M5 托管发布必须避开 `--prune`**：`cloudbase hosting deploy ./dist --safe` 足够；加 `--prune` 会删除本次产物之外的远端文件（本项目托管内既有 `__auth/*`、`cloud-admin/index.html`），属自毁。回滚口径＝按指定 commit 重建 `dist` 再发布（dist 可由源码重建，无需备份静态产物）。

## 30. CloudBase 用量治理 · 轮询聚合 · 签名有效性门（2026-10-26 提审前清零实证新增）

- **N1 触发器可能双份并存，是调用量翻倍的头号来源**：同一函数可同时存在「标准触发器（`config.json` 的 `triggers`）」与「微信云开发侧触发器」，二者各自触发、互不覆盖。排查/下线口径：
  1. `cloudbase fn detail <fn>` 看 `Triggers` 列表（两份都会列出）；
  2. **把 `config.json` 的 triggers 置空不会删除已存在的触发器**，必须 `cloudbase fn trigger delete <fn> <triggerName>`；
  3. 删除后 `fn detail` 复核 `Triggers: []`，并在台账记「删了哪一份、日减多少调用」。
  实证（2026-10-26）：`zz-warmup` 两份并存（标准 `0 */5 * * * * *` 288 次/天 + 微信云开发 `0 */5 7-22 * * * *` 192 次/天）= 480 触发/天 × 每次触发约 3 次调用 ≈ **1,440 调用/天**；`fn trigger delete` 需执行两次才清空。
- **N2 用量归因先做乘法，降频必须带回算表**：日请求量 ≈ Σ(触发/轮询次数 × 单次调用内 DB 读写次数)。先量化最大项再动手；任何降频方案必须同时给出「新触发次数/天 × 单次操作数 = 新日请求」与「业务可接受的最大延迟」。实证（2026-10-26）：`order-timer` 5 分钟 = 288 次/天 × 约 18–22 读 ≈ 5,760 DB/天，为最大头；降为 10 分钟后 144 次/天，代价是超时自动流转最多延迟 5 分钟。
- **N3 轮询三件套：聚合、增量、省写**：①把同一页面的多个轮询合并为一个聚合动作（实证：`chat_poll` 一次返回四确认 + 未读通知）；②增量拉取用**本批数据自身的最大 `created_at`** 作游标（`after_ts`），**禁止用服务端 `server_ts`**（会跳过「查询已执行、响应未返回」之间写入的消息）；③无变化场景不写库（实证：`im-conv.clearUnread` 未读为 0 直接返回）。降频必须同步复核时序契约（如消息 ≤15s、四确认/通知 ≤60s），不能只改数值。
- **N4 定时器下线要「删触发器 + 代码熔断」双保险**：无法立即删除或日后要恢复时，保留 handler 并在定时触发分支直接返回 `{skipped:true, reason:'<日期>_disabled'}`；手动调用（如 `{"action":"run"}`）仍可用。恢复时按**单触发器**重建（示例 `0 */15 7-22 * * * *`）、去掉熔断分支、重新部署并复测日曲线。
- **N5「文件完整性校验」≠「业务有效性校验」**：PNG 魔数/体积/SHA-256 只能证明文件存在且未被篡改，**不能证明签名可辨认、协议已理解或身份匹配**。凡提审/合规链路必须另设业务有效性门并给出用户可见的成功/失败反馈；「是否落笔」布尔不能替代「签名质量识别」（墨迹像素/占比/包围盒/单点检测）。实证（2026-10-26 测试反馈）：现存签名链路仅 `hasInk` 布尔 + 服务端 PNG/SHA-256 校验，无识别环节 → 已登记 tech-debt P0-4。
- **N6 提审前清零项必须台账化，并区分「已实施 / 仅登记」**：在 `tech-debt` P0 区按「问题｜根因｜已做｜测算｜提审前 owed｜状态」登记；用户明确「暂时不动代码」时**只改台账、零代码**；纯登记无版本变更时**不新增 CHANGELOG 变更行**（同一事实不双写），实施后再补 CHANGELOG 并订正台账状态。提交与 push 分离：提交前 `git status --short` 取证、排除用户 SOP 未跟踪文件；push 需用户明确指示（承接 §15）。
- 与既有规则关系：N1/N2 补充 §10（CloudBase 实战坑）与 §12（上线核验：改完取证）；N3 补充 §13（前端写操作提示时序）与 §23-H2（调用通道/身份矩阵）；N4 承接 §10 与 §23-H2；N5 承接 §12 与 §28-L3（预期态/有效性口径）；N6 承接 §9（收尾沉淀）、§14（commit 三类隔离）与 §15（Git push 绕代理）。

## 33. 默认值兜底链 · 门禁覆盖面 · 媒体 fileID 白名单（2026-10-27 昵称/头像编辑实证新增）

- **Q1「注册用户名不生效」类反馈先查默认值兜底链，不先怀疑写入失败**：显示层常用 `{{user.nickname || '微信用户'}}` 兜底，只要写入端没把用户设定值写进字段，页面就会恒显默认值，且看起来"像"实名/注册没生效。排查顺序：①DB 实读字段值（区分空串/null/默认字面量）；②写入端是否在关键节点（如实名通过）回写该字段；③显示层兜底文案是否掩盖了空值。实证（2026-10-27）：注册三条链路硬编码 `nickname:'微信用户'`、`update_profile` 云函数存在但前端零调用、`submit_realname_action` 只写 `real_name` → 实名后仍显示「微信用户」；处置=实名通过时若昵称空或为默认字面量则同批回写实名姓名（已有自定义昵称不覆盖），并对存量按 `nickname='微信用户' ∧ is_realname_done ∧ real_name 非空` 回填（nModified=1）。
- **Q2 门禁"全绿"只代表它扫过的范围，不代表全仓可发布**：`verify:offline` 的 SYNTAX 段只扫 `cloudfunctions/`（SYNTAX 262 = 云函数文件数），`miniprogram/` 前端 JS **不在覆盖内**。实证（2026-10-27）：`profile.js` 三元表达式漏 `:`，门禁 **EXIT=0**，体验版上传才报 `Syntax Error (code 10)` 失败。纪律：**改过前端 `.js` 后、上传体验版前，必须对改动文件跑 `node --check`**（必要时全量扫 `miniprogram/**.js`，2026-10-27 全量实测 0 bad）；新增/扩展门禁须按 §32-O7 双挂载，并先跑存量清点确认不会误伤。缺口已登记 tech-debt P3-19。
- **Q3 媒体字段改存云存储 fileID（`cloud://`）时，全链白名单必须同步放行**：项目里多处 `avatar` 过滤器写作 `/^https?:/`（防 openid 等脏值渲染），一旦头像改存 `cloud://`，这些位置会**静默过滤为空**（不报错、头像消失），排查成本高。纪律：改存储形态前先全仓 grep 该字段的所有 `https?:` 校验点（前端页面/组件 + 云函数输出侧），一并改成正则白名单 `^(https?:|cloud:\/\/)`；云端改动需同步部署（本轮 `user-login` + `home-action`）。实证（2026-10-27）：8 处过滤点（前端 profile / partner-detail / message / partner-card；云端 user-login/action_map、home-action/action_feed×2）。
- **Q4 用户自助编辑类入口的入参必须在服务端收口**：「前端零调用」的沉睡云函数一旦接入口，等于把未经校验的入参直接暴露；启封前先补齐 trim/长度/协议白名单与专属错误码。实证（2026-10-27）：`update_profile` 新增昵称 trim 后 1–20 字、头像仅 `cloud://`/`http(s)://` 且 ≤512 字符、错误码 `profile_avatar_invalid`，A/B 457 仍 EQUIVALENT。
