# 双代理交叉技术评审（zhaoren）

对一批已完成的提交（如技术负债整改、多批次重构）做独立交叉评审。
核心纪律：**每个问题必须 2/2 双确认才立项修复，1/1 低置信不修**。

## 为什么双代理

单轮评审（含 AI 评审者）的初判会出错。已实证案例：
- 评审者声称「HTTPS 挂起会跳过 order-timer 后续所有状态推进段」→ 双验证者证伪：
  demand_notify 是 main 的**最后一段**，S1 超时等推进段都在它之前。真实影响
  仅为 grab_notify_pending 未清 → 下轮重推。影响面描述错会误定级。
- grep 只搜云函数目录 → 误判「全库无登录失败锁定」；实际 `_shared/security_policy.test.js`
  的用例名就暴露了 user-login 端的 pwd_fail_count 机制。**grep 范围必须含 `_shared/` 测试文件**。

## 流程

### 1. 圈定评审范围
```
git --no-pager log --oneline <base>..HEAD        # 提交清单
git --no-pager diff --stat <base>^..             # 文件面
```
扣除基线快照/构建产物类机械改动，得出真实净改动量。

### 2. 拆两类任务，并行派两个子代理（Explore 型）

**代理 A（结构性问题猎手）**——prompt 要点：
- 给出 diff 范围与项目背景（_shared 多副本、串行部署、fail-closed 原则）
- 要求读真实代码验证，逐个报告：问题是否存在 / 影响面（引文件:行号）/ 置信度
- 重点类别：安全（公网暴露、鉴权旁路、凭据泄漏）、可靠性（无超时的外呼、
  Promise 挂起、静默吞错）、性能（重复初始化、无缓存外呼）、门禁盲区
- 明确要求：「验证我说的每一项，也要证伪——如果影响面描述错了请纠正」

**代理 B（定点抽查）**——选 3-5 个高风险文件（新增链路、安全相关 action）：
- 逐行核对行为等价性、密钥不泄漏、错误码契约
- 抽查结果与代理 A 的问题清单互补

### 3. 汇总与定级
| 置信度 | 处理 |
|---|---|
| 2/2 确认存在 | 立项修复 |
| 1/1 且可低成本验证 | 主对话自行读代码裁决 |
| 1/1 低置信 | 登记留存负债，不修 |

定级口径：P2=安全且可利用（如爆破不可见）；P3=可靠性缺陷或浪费型（重复调用、
无超时挂起）；P4=纯理论边界（记录不修）。

### 4. 输出评审报告
- 推断意图（这批改动想达成什么）
- 问题表（#/级别/问题/修复建议/代码位置 file:line 链接）
- **验证者修正**章节：评审初判被证伪的项，明示修正前后口径（防复发关键）
- mermaid 链路图（问题位置）+ 修复流程图
- 用文本让用户选修复项（A 全部 / B,C 部分 / E 不修），**不要擅自开修**

### 5. 修复纪律（用户选定后）
```
部署前先提交（工作区干净）→ 部署前 bundle 归档 → 串行部署受影响函数（一次一个，--remote-npm-install）
→ 部署后 download 核验标记串（admin-action=login_locked / init-db=dev_until / 通用 openid.js=invalidateEnvCache）
→ deploy-log 补登记行（含回滚点）→ commit（中文消息含评审来源/定级/验证证据）+ push
```
注：改代码流程内先「最小改动（注释注明「评审修复」来源）→ 补/改单测（新增行为必须有断言）→ npm run verify 全绿（含 A/B 等价）」，再进入上方部署链。反例（2026-10-13）：未先提交即部署，归档 bundle 只能取部署前 HEAD、回滚点含混，deploy-log 须特别注明——务必先提交。
部署后运行时验证（与 download 核验互补，可选）：order-timer 用 scripts/check-heartbeat.ps1 心跳确认（AWK_KEY 从 C:\zhaoren-bak\admin-key-20261009.txt 读）；admin-action 用网关 config_get 读回。

### 6. 收尾
- 修复后更新留存负债清单（memory 已有「留存负债」条目）
- git push 网络抖动直接重试；PowerShell 把 git stderr 渲染成 NativeCommandError
  属正常，以 `dba3a65..776d577` 类 range 输出判定成功

## 变体：非代码产物评审（衔接提示词 / 文档 / 方案）

投喂或发布前的把关（衔接提示词、runbook、方案文档），流程同双代理，角色换为：

- **代理 A（事实核验）**：把产物中每个可核查声明逐条列清单（哈希/计数/路径/数字/file:line/连通性），要求实测取证；输出「属实/不符/无法核验 + 置信度」。重点抓三类高频问题：
  ①数字凭记忆未实测；②**过时口径**（引用旧版本行为，如已修复的缺口仍写成现状——2026-10-13 实证：backup.ps1 的 confirm 已修复但提示词仍写「会导空」）；③状态漂移（产物写完后状态变化，如审核期间推送由失败转成功）
- **代理 B（完整性/偏离）**：对照用户模板（六段+回执校验+核对要点）与仓库现状查四类——遗漏（待办缺口/未闭环走查/用户侧风险清单）、矛盾（如「不主动 push」与推送指令并存）、误导（选项范围漏掉已决项）、自含性（无上下文读者能否仅凭产物开工）；附凭据明文扫描
- 技巧「**反向假设**」验声明/用例敏感性：改坏实现或调整关键参数，若断言仍全绿即为盲区（2026-10-13 实证：锁定阈值下调 1-4 无用例守护）
- 反哺纪律：2/2 或实测可证 → 立即修正产物并输出「变更清单」；1/1 → 主对话裁决
- 案例（2026-10-13 衔接提示词 v3）：审核发现 5 处修正（skills 入库数 18 非 19、backup.ps1 口径过时、推送状态改已推、已决项 #2 竞态须写明「登记不修」防全修、漏 user-side-todo 与另 5 项未跟踪文件去向）
