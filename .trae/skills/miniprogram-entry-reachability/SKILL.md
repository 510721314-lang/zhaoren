# 小程序入口可达性与门禁落点（zhaoren）

2026-11-15「选单模式」真机回归实证：三处体验断层同时爆发，根因同源——**能力建好了，但用户到不了**。
本技能把该次排查固化为可复用检查法，避免「功能已开发」被误当成「功能已可用」。

## 三条铁律

1. **唯一写入入口必须可达**：某字段的唯一可写 UI 若位于孤儿页（全仓零跳转引用），等价于该能力线上不存在。
2. **门禁文案落点必须真能解该码**：`missing` 返回 `switch_off` → 弹窗「去开启」必须落到**真有开关**的页面；落到语义相近但缺控件的页 = 用户永久卡死。
3. **安全能力入口不得只在单一身份分支内**：SOS / 紧急求助 / 报警的唯一入口若被 `wx:if="{{identity==='partner'}}"` 卡住，纯需求方或未入驻用户即无求助通道（红线口径通常不限定角色）。

## 取证方法（先取证再改，禁靠直觉）

### 1. 孤儿页判定

```
Grep "pages-v2/<页面名>" 全仓（miniprogram/）
```
- 只命中 `app.json` 注册行 + 页面自身 → **孤儿页**
- 命中点若是 `scripts/*.js` 自动化脚本 → 仍属孤儿（非用户路径）
- 命中点若是「内联卡片 / 同名文案」→ 不算入口，须看是否真的 `navigateTo` 该路径

### 2. 门禁闭环判定

对前端 `missing` / 云端拒绝码逐个走一遍：
```
1) 找到弹窗位置（grep confirmText / 拒绝码字符串）
2) 看 success 回调里的 url 落点
3) 打开落点页，grep 该门禁对应的控件（如 accept_switch / 开关 bindchange）
4) 控件不存在 → 断层成立
```

### 3. 双身份覆盖判定

```
Grep 该入口 wy:if / wx:else 所在分支
→ 确认另一身份（partner / user）是否有等价入口
```

## 修复决策（按优先级）

| 序 | 方案 | 适用 | 代价 |
|---|---|---|---|
| 1 | **能力下沉到语义正确的页** | 门禁文案与入驻链步骤已指向某页，而该页缺控件 | 最小；一处改动修通多条入口 |
| 2 | **补 1 行入口** | 页面功能完整、有通用路由映射（如 `onPartnerEntry`） | 最小；适合工作台/看板类页 |
| 3 | **抽公共组件/工具** | 两处以上需要同一能力，且逻辑涉及安全或资金 | 中等；须登记单一真相，禁双份实现 |
| 4 | 下线页面 | 能力已全部迁移、且无红线依赖 | 最大；须改 `app.json`，另案 |

> 判断法：先问「哪条既有入口承诺了这个能力」——承诺方（门禁文案、入驻链步骤、进度卡）指向哪页，就把能力放到哪页（方案 1），而不是反向加新入口。

## 落地检查清单

- [ ] 唯一写入口所在页，至少有 1 条用户可达路径（非自动化脚本）
- [ ] 每个「去XX」弹窗的落点页含对应控件
- [ ] 安全类能力在所有相关身份分支下都有入口
- [ ] 新增入口后 `node --check` + `check-miniprogram-syntax` + `check-silent-catch` 通过
- [ ] 台账登记：CHANGELOG 一行 + tech-debt（若留下未修项）+ REGISTRY 验收步骤
- [ ] 列为真机回归项（UI 入口改动静态门禁无法自证）

## 2026-11-15 实证案例（三断层）

| 断层 | 事实 | 修法 |
|---|---|---|
| 接单开关 | `accept_switch` 唯一写入 UI 在 `workbench` 页（孤儿页）；而广场「去开启」、我的页「去开启接单」、入驻链第 5/8 步三处都指向 `accept-config`（无开关） | 开关下沉到 `accept-config` 页首（方案 1，2 文件 ~27 行） |
| 工作台不可达 | `workbench` 全仓零跳转，但其承载 `free_sos`（无单求助）唯一前端入口 | `partnerEntries` 补 1 行（方案 2） |
| 非耍伴无求助 | 入口卡在 `identity==='partner'` 分支，而云端 `free_sos` 不校验角色 | 抽 `utils/free-sos.js` 单一真相 + 用户工作台补入口（方案 3） |

**校验旁证**：第二、三条修复均在「不动云函数」下完成——先 grep 云端确认无角色校验，避免误改后端。
