# 纠纷处理/申诉历史汇总 + 退款可设金额 · 实施方案

## Context（为什么做）

后台「纠纷处理」页（`Dispute.vue`）当前存在三个问题：

1. **「纠纷原因」列恒空** —— 管理端读 `order_main.dispute_reason`（admin-action L1310），但写入侧 order-action 的投诉分支写的是 `complaint_reason`（order-action L1362），字段名不一致导致后台看不到原因。
2. **看不到「过程」** —— 列表只展示当前状态与一条处置备注，没有把「发起投诉 → 客服开案 → 双方举证 → 裁定 → 退款」的全链路留痕（操作人/时间/金额/备注）汇总呈现；已处置完的历史单据（S7/S5）也从列表消失（`dispute_list` 只查 S10/S10.5）。
3. **退款不能设金额** —— 裁决退款只做 `S10.5 → S7` 的状态翻转，不写退款流水、不发通知、金额固定为订单全额（admin-action L1328-1342）。

本次目标（用户已确认口径，**提审前完成**）：
- 后台可汇总查看纠纷与申诉的**历史及过程**：列表 + 点击行打开**详情抽屉时间线**。
- 裁决退款支持**输入金额**（可部分退款，≤ 可退上限），并**写退款流水 + 通知双方**。

## 设计口径（关键决策）

| 决策点 | 结论 | 理由 |
|---|---|---|
| 可退上限 | `refundable = total_fen − 已成功退款合计`，**不含 `tip_total_fen`** | 支付流水 `type='pay'` 金额即 `total_fen`；小费走独立流水，纳入会重复退款且破坏对账 |
| 缺省金额 | 不传 `refund_fen` 时回落 `order.total_fen`（等价历史全额） | 向后兼容旧前端/手工调用 |
| 退款流水落表 | **复用 `pay_transaction`（type='refund'）**，不新建集合 | `finance_list` 已读该表、`idx_order_id` 已存在、`order_detail` 已聚合，免去 4 处集合登记 + 索引 + 台账 |
| 分账字段 | **不改** `partner_income_fen / fee_fen` | 退款终态 S7 不再进 `settlement` 聚合；部分退款的差额结算属新业务，提审前只记 `refund_fen` + 流水（代码留 TODO） |
| 通知类型 | 复用 `system_notice.type='refund'` | `order-action notice_list` 无 type 白名单，小程序消息页按 `action_key` 跳转，不会丢 |
| 列表范围 | 新增 `scope=active|history|all`，**默认 active**（与现状完全一致） | 向后兼容，另提供已处置历史视图 |
| 前端展示 | 详情用 `el-drawer` + `el-timeline` | 复用 `Orders.vue` L74 / L91-96 既有样板 |

## 改动清单

### 1. `cloudfunctions/admin-action/index.js`（核心，★必须串行部署）

- **`genPayNo(prefix)`**：照 `payment-mock/index.js` L34-41 内联一份（`crypto` 已在 L6 require，直接用）。产出 `REF + YYYYMMDD + 16hex`。
- **`dispute_handle` 改造**（L1317-1359）：
  - 新增 `refund_fen` 解析与校验（仅 `decision==='refund'`）：
    - 先查 `pay_transaction` 中 `{order_id, type:'refund', status:'success'}` 的 `amount_fen` 合计得 `alreadyRefunded`；`refFenMax = total_fen − alreadyRefunded`。
    - `!Number.isInteger(refFen) || refFen <= 0` → `fail('dispute_bad_amount', '退款金额须为正整数分')`。
    - `refFen > refFenMax` → `fail('dispute_amount_exceed', '退款金额不得超过可退上限 ¥X.XX')`。
  - `patch` 追加：`refund_fen, refund_no, refund_source:'dispute', refund_by: openid, refunded_at: now`（不写 `refund_status`，以流水 status 为准）。
  - CAS 抢占保持 `where({_id, status: before})`（L1344）不变 → 天然防双退。
  - CAS 成功后、退款分支写 `pay_transaction`：`{pay_no: genPayNo('REF'), order_id, order_no, type:'refund', amount_fen: refFen, channel:'mock', is_mock:true, status:'success', source:'dispute', operator_openid: openid, note, paid_at, created_at, updated_at, is_deleted:false}`。
    - 写失败**必须补偿**（复刻 `mock_refund` L390-396）：`where({_id, status:'S7'}).update({status:'S10.5', refunded_at:0, refund_fen:0, refund_no:'', updated_at})` 后返回 `fail('refund_db_fail', ...)`。
  - 通知双方（`await Promise.allSettled`，复刻 `mock_refund` L400-412），文案含金额：用户「退款成功 / 争议裁决退款 ¥X 已原路退回」、耍伴「订单已退款 / 该订单争议裁决退款 ¥X」，均 `action_key:'jump_order'`。
  - `order_status_log` 的 `note` 附带退款金额（便于时间线展示）。
  - `logEvent('P2', 'dispute_refund', ...)` detail 带上 `refund_fen`。
- **新增 `dispute_detail` action**（放在 `dispute_handle` 之后）：
  - `ROLE_GRANTS` 增 `'dispute_detail': ['R2','R3']`。
  - 入参 `{order_id}`，`isDocId` 校验。
  - 并行取四源：`order_status_log`(asc,100) / `complaint`(asc,20) / `no_show_report`(asc,20) / `pay_transaction`(asc,50)。
  - 批量解析 `user_account.nickname`（`_.in(openids)`, ≤20），失败降级为角色标签；`roleOf(oid)` 判定 用户/耍伴/客服·系统。
  - 内联 `STATUS_LABEL`（云函数侧无 enums 模块）：`S0 待支付 / S1 待确认 / S2 履约中 / S3 已确认 / S3.5 履约完成 / S4 部分完成 / S5 已完成 / S6 已取消 / S7 已退款 / S8 已结算 / S9 已评价 / S10 已关闭 / S10.5 争议处理中`。
  - 归一到统一 timeline 元素 `{ts, tag, title, desc, actor_text}`（tag ∈ status/complaint/nosh/money），按 `ts` 升序排序后返回。
    - status：来自 `order_status_log`，标题「原状态 → 新状态」，desc 取 `note || action`。
    - complaint：来自 `complaint`，「发起投诉 / 投诉已撤回」，desc = reason。
    - nosh：来自 `no_show_report`，拆多条：提交(`created_at`)、举证(`defense_at`，字段已确认存在)、裁定(`decided_at`)、撤回(`withdrawn_at`)。
    - money：来自 `pay_transaction`，「支付/退款 ¥X」，desc = pay_no。
  - 返回：`{ order(脱敏+纠纷相关字段: complaint_reason/admin_note/dispute_opened_at/dispute_handled_at/refunded_at/refund_fen/customer_nick/partner_nick), timeline, no_show_reports, complaint, transactions }`。
- **`dispute_list` 扩展**（L1297-1315）：
  - `scope` 白名单 `['active','history','all']`，默认 `active`：
    - active：`status: _.in(['S10.5','S10'])`（= 现状）
    - history：`dispute_handled_at: _.gt(0)`
    - all：`_.or([{status: _.in(['S10.5','S10'])}, {dispute_handled_at: _.gt(0)}])`
  - 返回行补：`complaint_reason: o.complaint_reason || o.dispute_reason || ''`（**修恒空 bug**）、`dispute_reason`、`dispute_handled_at`、`dispute_opened_at`、`refund_fen`。
- **`EXPORT_COLLECTIONS`**（L3008-3030）增 `'complaint'`。

## 验证（端到端）

前置：`gate.ps1` 全绿 → commit → **串行**部署 `admin-action` → admin-web（`npm run build` → 清空重拷 `dist/*` 到 `cloudfunctions/admin-web/public/` → 部署 `admin-web`）。

人工用例：
1. **原因显示**：找一条有 `complaint_reason` 的 S10.5 单 → 后台列表「纠纷原因」非空。
2. **部分退款**：争议单裁决退款，输入 `1.00` → 提示成功；查 `pay_transaction` 出现 `REF*` 记录 `amount_fen=100`；`order_main.status=S7` 且 `refund_fen=100 / refunded_at / refund_no` 有值。
3. **超额拒绝**：输入 `total+1分` → 报「不得超过可退上限」。
4. **历史视图**：`scope=全部` 可见刚处置的 S7 单；`scope=已处理` 只列已处置单。
5. **时间线**：打开详情抽屉，含 发起投诉 / 开案 / 退款 节点，操作人可读（非裸 openid），退款节点显示金额。
6. **通知双方**：用户与耍伴各收到 1 条含金额的退款通知，点击跳订单详情。
7. **并发**：两窗口同时点退款 → 仅一方成功，另一方 `dispute_conflict`。
8. **申诉时间线**：爽约申诉详情内时间线正确（提交/举证/裁定/撤回）。

构造 mock 数据：控制台用 `mock_openid` 调 `order-action complaint` 造 S10.5 单，或直接控制台改 `order_main.status='S10.5'`。
