# 接单配置三项改造方案（时段生效 / 价格区间 / 每日限单后台化）

## Context（为什么做）

用户真机实测反馈三件事，根因已定位：

1. **接单时段"设置不起作用"** —— `miniprogram/pages-v2/accept-config/accept-config.js` 的 `onSave()`（L247-297）只把 `accept_scenes / scene_rates / home_location` 传给云函数，**其余参数（weeklySlots 时段、minPrice、maxDistance、genderPref、dailyLimit、acceptWelfare、bufferMin）全部只写本地 Storage（L278-289）**，云端零痕迹 → 服务端无从校验；且换设备/清缓存即丢。附带缺陷：时段 UI 用 `picker mode="time"`（单值选择）却显示 `09:00-18:00`（范围），结构本身不匹配。
2. **只有最低单价、没有最高单价**，且价格参数在接单与查询链路完全未被使用。
3. **每日接单上限** 目前是耍伴端本地滑块，需纳入后台统一管理并服务端生效。

目标：三类参数在云端可存、服务端可校验、UI 符合"显眼滑动条 + 只读展示"的要求。

## 已确认口径（用户拍板）

| 项 | 口径 |
|---|---|
| 价格区间 | **广场列表过滤 + 抢单硬拦**（需求时薪超出区间则不展示、不可接） |
| 每日上限 | **后台统一设定，耍伴不可改**（前端只读展示） |
| 接单时段 | **需求的服务时间段必须完全落在启用时段内**，否则拒接 |

## 一、数据模型（`partner_profile` 新增字段，均经 `update_config` 写入）

```js
weekly_slots: {                       // 7 天；分钟数(本地/东八区)，0-1440
  mon: { enabled: false, start: 540, end: 1080 },  // 09:00-18:00
  ... tue/wed/thu/fri/sat/sun
},
accept_rate_min_fen: null | int,      // 分/小时；null = 不限（默认）
accept_rate_max_fen: null | int
```

**老数据兼容（关键）**：字段缺失 ⇒ **视为不限**（时段不拦、价格不拦），只有耍伴显式保存后才收紧；避免存量耍伴集体失去接单能力。

**两代时段格式解析器**（云端唯一入口，兼容旧 `{enabled, time:'09:00-18:00'}` 字符串）：

```js
function parseSlot(s) {
  if (!s) return null;
  if (typeof s.start === 'number') return { enabled: !!s.enabled, start: s.start, end: s.end };
  const m = /^(\d{1,2}):(\d{2})-(\d{1,2}):(\d{2})$/.exec(String(s.time || ''));
  return m ? { enabled: !!s.enabled, start: +m[1] * 60 + +m[2], end: +m[3] * 60 + +m[4] } : null;
}
```

**读侧钳制**：`lo = clamp(profile.accept_rate_min_fen, cfg.rate_min_fen, cfg.rate_max_fen)`，防止后台调整费率边界后老区间越界。

## 二、云端改动（5 个云函数）

### 2.1 `cloudfunctions/partner-action/index.js` — `update_config`（L261-333）
白名单内新增三个字段的接收与校验：
- `weekly_slots`：逐日校验 `enabled` 为布尔、`start/end` 为 0-1440 整数、`start !== end`；`start > end` 视为跨夜槽
- `accept_rate_min_fen` / `accept_rate_max_fen`：整数分，落在 admin_config `rate_min_fen ~ rate_max_fen`，且 `min < max`；传 `null` 表示清除（回"不限"）
- 保留既有：场景白名单、每场景时薪必填、多余 key 拒绝、home_location 校验

### 2.2 `cloudfunctions/order-create/index.js` — `create_from_take` 新增三段校验
插入位置：现有 scene 校验（L291）之后、订单创建之前。

```js
// A. 价格区间（只在耍伴显式设置时拦）
const [lo, hi] = readRateRange(profile, config);          // null = 不限
if (lo != null && demand.rate_fen < lo) {
  return { ok:false, code:'order_rate_out_of_range', msg:`该需求单价 ¥${demand.rate_fen/100}/小时，低于你的最低单价 ¥${lo/100}/小时` };
}
if (hi != null && demand.rate_fen > hi) { /* 对称：高于最高单价 */ }

// B. 服务时段（复用已有 newStart/newEnd）
if (!slotCovers(profile.weekly_slots, newStart, newEnd)) {
  return { ok:false, code:'order_slot_not_covered', msg:'该服务时段不在你启用的接单时段内，可在接单配置调整' };
}

// C. 当日接单上限（放最后，代价最高）
const limit = Number(config.partner_daily_take_limit) || 5;
const d0 = cnDayStart(Date.now());                        // 东八区 00:00
const cnt = await col('order_main').where({
  partner_openid: openid, is_deleted: false, status: _.nin(['S6']),
  created_at: _.gte(d0).and(_.lt(d0 + 86400000))
}).count();
if ((cnt.total || 0) >= limit) {
  return { ok:false, code:'order_daily_limit', msg:`今日接单已达上限 ${limit} 单，明天再来` };
}
```

- `slotCovers(slots, startTs, endTs)`：把服务区间按本地自然日切片，逐片要求 `[片起,片止) ⊆ [slot.start, slot.end)`；跨夜槽（`start > end`）覆盖集为 `[start,1440) ∪ [0,end)`；**跨午夜服务**必须次日槽也 enabled 且覆盖剩余片段，否则拒
- 当日计数**排除 S6（已取消）**，避免"接了退"刷量
- 并发说明：count 与 add 非原子，极端并发可能多 1 单，记 P3（后续可用计数字段/事务）

### 2.3 `cloudfunctions/admin-action/index.js` — 新增可配置字段
- `config_set` 的 `intFields`（L1191-1216）追加：`['partner_daily_take_limit', 1, 50]`（审计自动生效：`touch()` → `logEvent('P2','config_change',...)`）
- `config_get`：顶层加 `partner_daily_take_limit`（默认 5）+ `operations` 镜像块同步（后台 `Operations.vue` 读这里）
- `config_public`（L159-192）：新增 `partner_accept: { daily_take_limit }`（供小程序只读展示）
- 价格边界**复用**既有 `rate_min_fen / rate_max_fen`，不新增字段

### 2.4 `cloudfunctions/home-action/index.js` — 广场列表按价格区间过滤
- 引入 `resolveOpenid`（openid.js 已导出，但 index.js 从未调用）；**容错**：取不到 openid 或非已通过耍伴 → 返回 `null` 区间（不过滤）
- 新增 `loadVisitorRateRange(openid)`：查 `partner_profile` 取区间并钳制；结果可进程内短缓存
- **只改 `square`**：把该查询并入现有 `Promise.all`（不增 RTT），有区间时用 `hallWhere({ rate_fen: _.gte(lo).and(_.lte(hi)) })` 把过滤**下推到 DB**（保证 limit 50 仍能取满）
- ⚠️ 修正：`scene_groups` / `scene_list`（首页宫格数据源）**不按价格过滤** —— 首页是通用入口（含需求者/游客视角），用"接单价格"过滤首页语义错误

## 六、验证步骤（端到端）

1. **后台字段**：Operations.vue 设 `partner_daily_take_limit=1` → 保存 → `config_get.operations` 回显 → 小程序接单配置页显示只读「1 单/天」
2. **时段生效**：滑动条设周一 09:00-12:00 → 保存 → 云端 `weekly_slots.mon = {start:540,end:720}`；造一个**周一 14:00** 的 matching 需求 → 控制台 `order-create create_from_take` 期望 `order_slot_not_covered`；改到 10:00 期望 `ok:true`
3. **价格区间**：`update_config` 传 `accept_rate_min_fen=5000` → 造 `rate_fen=4000` 需求 → 抢单期望 `order_rate_out_of_range`；且 `home-action square` 的 list 里**不出现**该需求
4. **每日限单**：当日已有 1 单再抢 → `order_daily_limit`；次日 00:00 后恢复
5. **回归**：无 `weekly_slots` / 无价格区间的老 profile 仍可接单、广场可见（不过滤不拦截）
6. `node scripts/check-ssot.js` + `node scripts/check-nightmask.js` exit 0；改动的 JS 全量 `node --check`

## 七、风险与缓解

| 风险 | 缓解 |
|---|---|
| 老数据被误拦 | 缺字段=不限 + 惰性收紧，仅显式保存后生效 |
| 价格过滤导致耍伴看不到单 | 默认区间=平台全区间（等价不限）；广场空态文案提示"可在接单配置调整价格区间" |
| 后台改费率边界致老区间越界 | 读侧 clamp 到 `rate_min_fen~rate_max_fen` |
| 跨午夜服务判定复杂 | 按自然日切片逐段判定；R1 红线本已限制 23:00-06:00，跨日属边缘 |
| 当日计数并发 | 弱一致（可超 1 单），记 P3，后续用事务/计数集合 |
| square 延迟增加 | 过滤下推 DB；使用方查询并入既有 `Promise.all`，不增 RTT |
| 硬编码卷土重来 | 步长/边界/上限全部来自 CONFIG 或 admin_config，`check-ssot.js` 兜底 |
